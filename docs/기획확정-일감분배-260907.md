## 1. 게임 개요

### 1-1. 한 줄 정의

> 바탕화면에 원숭이와 나무를 띄워두고, 타자를 칠 때마다 원숭이가 나무를 펀치해서 바나나를 떨어뜨리고, 그 바나나로 **내 마우스 커서를 꾸미는** 방치형 PC 게임.

### 1-2. 5개의 축

| # | 축 | 역할 | 우선순위 |
|---|---|---|---|
| 1 | 코어 루프 (펀치 → 수확) | 재화 획득. 즉각 피드백의 원천 | **P0** |
| 2 | 마우스 커서 꾸미기 | 재화 소비처. 이 게임의 목적이자 차별화 훅 | **P0** |
| 5 | 누적 타수 = 레벨 | 빈 나무 구간의 공백 메움. 멀티 자랑 지표 | **P0** (저비용) |
| 3 | 멀티플레이 (관전형) | 리텐션·바이럴 | P1 |
| 4 | 강화 | 장기 목표, 커브 조절 손잡이 | P2 (조건부) |

**설계상 왜 이 기획이 이전 3안보다 나은가**

- 검토 §2-1 "방치형인데 방치하면 안 자란다"를 구조적으로 해결했다. **성장은 시간(나무의 바나나 열림), 수확은 타이핑.** 자리를 비워도 나무는 자라고, 돌아와서 수확한다. 방치형 기대와 타이핑 재미가 충돌하지 않는다.
- 검토 §2-3 "어뷰징 = 성취 붕괴"도 구조적으로 해결됐다. **열린 바나나 수가 상한이라 연타로 무한 파밍이 불가능하다.** 초당 캡은 보조 장치일 뿐, 경제가 이미 시간에 묶여 있다.
- 검토 §4의 결론(Punchy 코어 + 끼끼 메타)과 정확히 일치한다. 즉각 피드백은 펀치가, 장기 목표는 커서 수집이 담당한다.

**아직 남은 약점**

- 검토 §2-4 "즉각 피드백이 진짜 재미". **나무가 비어 있는 시간이 게임 시간의 대부분이다.** 5번(타수 카운터)만으로는 부족하다. 빈 나무를 쳐도 원숭이는 펀치하고 나무는 흔들려야 한다. 아래 §2-3에서 사양화한다.

### 1-3. 남은 미검증 리스크 — 커서 꾸미기

통과한 POC는 "투명 창 + 저부하"다. **"마우스 커서를 꾸민다"는 별개 기술이고 아직 검증 안 됐다.** 이게 게임의 핵심 축이므로 W1 Day 1-2에 최우선으로 스파이크한다.

가능한 3가지 방식과 판단:

| 방식 | 내용 | 판단 |
|---|---|---|
| A. `SetSystemCursor` | 시스템 커서 리소스 자체를 교체 | **불가.** 전역이라 크래시하면 유저 커서가 복구 안 된 채 남는다. 백신 오탐 소지도. |
| B. 시스템 커서 숨기고 직접 그리기 | `ShowCursor(FALSE)` + 오버레이에 커서 렌더 | **불가.** 다른 앱/전체화면 게임 위에서 깨진다. 앱 죽으면 커서가 사라진다. |
| C. 커서 추종 오버레이 창 | 시스템 커서는 그대로 두고, 클릭 통과 투명 창을 커서 좌표에 붙여 장식만 그린다 | **채택.** 안전하고, 실패해도 유저 환경이 망가지지 않는다. |

C 방식이면 "커서 꾸미기"는 정확히는 **"커서에 액세서리가 따라붙는다"**가 된다. 기획도 이 표현으로 확정한다:

- 커서 **본체**는 건드리지 않는다 (Windows 기본 커서 유지)
- 커서 **주변**에 장식이 붙는다: 매달린 원숭이, 따라오는 바나나, 트레일, 커서 뒤 후광
- 이게 오히려 v0.2의 "커서 원숭이" 원안과 같고, GIF 한 장으로 설명되는 마케팅 자산이라는 장점도 그대로다

**W1 스파이크에서 반드시 실측할 것**

1. 커서 좌표 폴링 주기 vs CPU (16ms/33ms/50ms 비교, 목표 유휴 1% 이하)
2. 창 이동 지연 — 커서와 장식 사이 고무줄 현상. 스프링 보간으로 오히려 "매달린" 느낌을 살릴 수 있는지
3. 멀티모니터 경계를 넘어갈 때
4. 전체화면 게임 / 브라우저 / 작업표시줄 위에서의 동작
5. 클릭 통과가 확실한가 (드래그·선택·우클릭 전부)

**여기서 막히면**: 커서 장식을 "마우스 근처에 상주하는 작은 원숭이" 수준(고빈도 추종 없이 느슨하게 따라옴)으로 낮춘다. 그래도 안 되면 커서 축을 접고 "원숭이 개체 수집 + 바탕화면 배치"로 재화 소비처를 옮긴다. **W1 Day 2에 판정한다.**

## 2. 코어 루프 사양

### 2-1. 구성

```
나무 (슬롯 N개)
  └ 각 슬롯: [비어있음] --(성장 타이머)--> [바나나 열림]
                                              │
유저 타이핑 ──> 원숭이 펀치 ──────────────────┘
                                              ↓
                                        바나나 낙하 → 획득 (+재화)
```

### 2-2. 수치 (1차안, W2에 튜닝)

| 항목 | 기본값 | 근거 |
|---|---|---|
| 나무 슬롯 수 | 3 | 강화로 최대 8까지 확장 |
| 바나나 성장 주기 | 슬롯당 8분 | 강화로 최대 3분까지 단축 |
| 펀치 1회당 수확 | 열린 바나나 1개 | 강화로 낙하 시 +보너스 개수 |
| 시간당 획득량 (기본) | 약 22개 | 3슬롯 / 8분 |
| 하루 8시간 켜둘 때 | 약 180개 | 리텐션 계산 기준 |

**오프라인 규칙**: 게임을 껐거나 자리를 비운 동안에도 나무는 자란다. 단 **슬롯이 상한**이다. 3슬롯이면 24분이 지나면 포화. 즉 **슬롯 수 = 오프라인 저장고 크기**이고, 이게 "가끔 돌아와서 수확한다"는 방치형 리듬을 만든다. 슬롯 확장 강화가 사실상 "오프라인 저장고 확장"이다.

**성장 커브**: 커서 아이템 가격을 5티어로 잡고 로그 스케일로 벌린다.

| 티어 | 가격(바나나) | 기본 획득 기준 도달 시간 | 성격 |
|---|---|---|---|
| T1 | 10 | 약 30분 | 첫 30분에 2~3개 확보. 초반 이탈 방지 |
| T2 | 40 | 약 2시간 | 첫날 |
| T3 | 150 | 약 7시간 | 2~3일차 |
| T4 | 500 | 약 하루 | 1주차 |
| T5 | 1,500 | 약 3일 | 장기 목표 / 도감 완성 |

검토 §2-2에서 지적한 "초반 30분에 3~4단계 몰아주고 이후 로그 스케일" 원칙을 따랐다. 강화를 넣으면 후반 티어의 실제 도달 시간은 절반 이하로 줄어든다.

### 2-3. 마이크로 피드백 (P0 — 이게 없으면 게임이 아니다)

**빈 나무를 칠 때도 반드시 반응이 있어야 한다.**

| 타이밍 | 반응 |
|---|---|
| 타이핑 1타 | 원숭이 펀치 애니메이션 (3~4종 랜덤 교차, 반복감 제거) |
| 펀치가 나무에 닿음 | 나무 전체가 흔들림 (진폭 작게), 잎 1~2장 파티클 |
| 바나나 열림 순간 | 나무에 반짝임 1회 + 아주 짧은 사운드 (옵션 Off 가능) |
| 바나나 낙하 | 낙하 애니 + 착지 튐 + 카운터 숫자 증가 애니 |
| 타수 카운터 | 매 타마다 증가. 자릿수가 바뀔 때 강조 |

검토 §3의 관찰("키 입력과 애니메이션을 1:1 고정 대응시키지 말 것")을 그대로 적용한다.

## 3. 커서 꾸미기 (재화 소비처)

### 3-1. 장착 슬롯

커서 1개에 동시에 붙일 수 있는 슬롯 3개:

| 슬롯 | 내용 | 초기 물량 |
|---|---|---|
| **매달린 원숭이** | 커서에 매달려 흔들리는 원숭이 | 6종 (색/품종/표정) |
| **트레일** | 커서를 따라오는 잔상. 바나나 조각, 잎, 반짝임 | 6종 |
| **후광/베이스** | 커서 뒤에 깔리는 작은 장식 | 4종 |

총 16종. 도감으로 관리하고, 조합으로 개성이 나온다.

### 3-2. 상점

- 재화는 바나나 단일. **현금 결제 없음** (1.0 기준)
- 상점은 전 상품 상시 노출. 랜덤 뽑기 없음 — 1달짜리 게임에 확률 UI를 붙일 이유가 없고, 유저가 "다음 목표"를 눈으로 볼 수 있어야 커브가 작동한다
- 구매 즉시 인벤토리에 들어가고, 장착 화면에서 슬롯에 끼운다

### 3-3. 도감

수집률 %를 메인 화면 구석과 멀티 룸에 표시. 100% 달성 시 스팀 도전과제.

## 4. 멀티플레이 (관전형)

**확정 범위: Steam Lobby + P2P 상태 브로드캐스트. 전용 서버 없음.**

### 4-1. 사양

| 항목 | 내용 |
|---|---|
| 룸 생성 | 유저가 룸 생성. 최대 인원 4명 (대역폭·화면 공간 고려) |
| 입장 | Steam 친구 목록 초대 / 룸 UID 직접 입력 |
| 표현 | 입장한 유저 각자가 **본인의 나무 + 원숭이 + 장착 커서**로 렌더링됨 |
| 동기화 대상 | 타건 이벤트(펀치 트리거), 수확 이벤트, 누적 타수, 장착 커서 정보, 도감 % |
| 동기화 안 하는 것 | 재화 잔액, 나무 성장 타이머, 강화 수치 — **경제는 전부 로컬** |
| 전송 | Steam P2P (unreliable). 타건은 개별 전송하지 않고 **200ms 단위로 묶어 전송** |

**경제를 동기화하지 않는 게 핵심이다.** 그래서 치트 방어 서버가 필요 없고, 검토 §2-3이 우려한 "멀티 넣으면 서버 신뢰 문제로 확 커진다"를 피한다. 멀티에서 보이는 건 **행동과 자랑 지표**뿐이다.

### 4-2. 멀티에서 얻는 경험

- 친구가 지금 일하고 있구나 (타건 리듬이 보인다)
- 친구가 방금 바나나를 땄다 (토스트)
- 친구 커서가 어떻게 꾸며져 있나
- 누적 타수 랭킹 — 룸 내 정렬

### 4-3. 공동 나무 — 조건부

W3 목요일에 **Go/No-Go 판정**한다.

- **Go 조건**: W3 수요일까지 4-1 범위가 다 돌고, 공동 나무 추가에 3일 이하로 추정될 것
- 넣는다면: 룸 중앙에 공동 나무 1그루. 룸 전원의 타건이 누적되어 열리고, 열리면 **전원에게 동일 보상**. 뺏기는 구조 아님(경쟁 붙이면 어뷰징 압력이 생긴다)
- 호스트 권위: 공동 나무 상태는 호스트가 관리. 호스트 이탈 시 공동 나무는 리셋되고 룸은 유지

**No-Go면 그냥 뺀다.** 1.0에 없어도 게임이 성립한다.

## 5. 강화 (P2, 조건부)

**W3에 시간이 남으면 넣고, 안 남으면 1.1로 뺀다.** 다만 **W1의 수치는 강화가 붙는다는 전제로 설계**해서, 나중에 붙일 때 밸런스를 다시 안 짜도 되게 한다.

3축:

| 축 | 효과 | 기획 의도 |
|---|---|---|
| 원숭이 파워 | 펀치 1회당 수확량 +1씩 | 타건당 체감 보상 |
| 나무 주기 | 성장 주기 8분 → 최소 3분 | 시간당 총량 |
| 나무 슬롯 | 3 → 최대 8 | 오프라인 저장고 |

강화 비용은 커서 아이템과 **같은 바나나를 쓴다.** 꾸미기 vs 효율 사이의 선택이 생기고, 이게 방치형에서 검증된 긴장 구조다.

## 6. 누적 타수 = 레벨

- **성장이 아니라 기록이다.** 타수로는 재화를 얻지 못한다. 나무에 열린 것만 재화가 된다
- 누적 타수를 로그 스케일로 레벨 환산. 레벨은 자랑용 숫자이고 게임 밸런스에 영향 없음
- 멀티 룸에 표시. 이게 "이 게임에 쏟은 시간"의 증거

**어뷰징 방어**: 재화가 아니므로 압력이 낮지만, 랭킹 신뢰를 위해 최소 방어는 넣는다.
- 초당 10타 캡
- **타건 간격이 규칙적으로 이어지면 5타 이후 감쇠** (자동 반복·매크로가 여기 걸린다)

> **2026-09-14 변경.** 원래 사양은 "동일 키 연속 입력 시 5타 이후 감쇠 / 자동 반복은
> 1타로 처리" 였다. 그런데 **같은 키인지 알려면 키 코드를 읽어야 하고, 그건 §7-2 의
> "키 코드를 읽지 않는다" 와 정면으로 충돌한다.** §10 이 개인정보 문구를 "절대 자르지
> 않는 것" 에 넣었으므로 프라이버시 쪽을 우선했다.
>
> 기준을 키 동일성에서 **타건 간격의 규칙성**으로 바꿨다. 사람의 간격은 들쭉날쭉하고
> 매크로·키 홀드는 메트로놈처럼 규칙적이라 키 코드 없이 갈린다. 자동 반복도 고정
> 주기라 같은 장치에 걸리므로 별도 규칙이 필요 없다.
>
> **오히려 더 넓게 막는다** — 서로 다른 키를 번갈아 누르는 매크로까지 잡히고,
> 그건 원래 규칙으로는 못 잡던 것이다. 실측 결과는 docs/A4-GLOBAL-INPUT.md §4.

## 7. 시스템·비기능 사양 (검토 §8에서 누락 지적된 항목)

### 7-1. 오버레이 셸

- 창: 투명 + 무테 + 항상 위 + 클릭 통과. 나무/원숭이 영역만 클릭 판정 활성
- 위치·크기 저장, 재실행 시 복원
- 멀티모니터 / DPI 스케일링 대응
- 전체화면 게임 위에서는 자동 숨김 (옵션)

### 7-2. 글로벌 입력

- **RawInput (WM_INPUT)** 방식 확정. `WH_KEYBOARD_LL`은 쓰지 않는다
- **키 코드를 읽지 않는다.** 입력 발생 사실만 카운트. 코드 레벨에서 증명 가능한 구조로 작성
- 배포 전 검증: Defender 실시간 검사 하에서 실행 / VirusTotal 오탐 엔진 수 / Vanguard·EAC 켠 상태에서 충돌 여부

### 7-3. 저부하

- 유휴 시 CPU 1% 이하, 노트북 배터리 영향 없음
- `low_processor_usage_mode` + `Engine.max_fps` 동적 조절
- 애니메이션이 없을 때는 프레임을 떨군다. 타건이 오면 즉시 올린다
- **커서 추종 창을 포함해서** 실측한다 (여기가 새 부하 요인)

### 7-4. 옵션 화면

크기 / 투명도 / 위치 잠금 / 사운드 On-Off / 알림 On-Off / 커서 장식 On-Off / 전체화면 앱 위 숨김 / 자동 시작 / 타수 카운트 On-Off(폴백용)

### 7-5. 세이브

- 위치: `%APPDATA%/<게임명>/save.json`
- 스키마 버전 필드 필수, 마이그레이션 훅 준비
- 저장은 임시 파일 쓰고 원자적 교체 (상주 앱이라 강제 종료가 잦다)
- 자동 저장: 60초 주기 + 수확/구매 시 즉시

**스키마 v1 (W1 Day 1에 둘이 합의하고 고정)**

```json
{
  "version": 1,
  "bananas": 0,
  "totalKeystrokes": 0,
  "tree": { "slots": 3, "growthMs": 480000, "slotTimers": [0,0,0] },
  "upgrades": { "power": 0, "cycle": 0, "slots": 0 },
  "inventory": { "owned": ["monkey_01"], "equipped": { "hang": "monkey_01", "trail": null, "base": null } },
  "settings": { "scale": 1.0, "opacity": 1.0, "pos": [0,0], "sound": true, "autostart": false },
  "lastQuitUtc": "2026-09-07T00:00:00Z"

```

### 7-6. 개인정보·보안 방침

스토어 페이지 + 게임 내 최초 실행 시 동일 문구 노출:

> 이 게임은 타이핑 **횟수**만 셉니다. 어떤 키를 눌렀는지 읽지 않고, 저장하지 않으며, 외부로 전송하지 않습니다.

멀티 전송 데이터 목록도 명시한다 (타건 발생 여부 / 수확 이벤트 / 누적 타수 / 장착 정보 — 그 외 없음).

## 8. 2인 역할 분담

### 8-1. 분할 기준

둘 다 비슷한 수준의 클라 개발자이므로, **기술 난이도가 아니라 의존 관계로 나눈다.** 서로를 기다리는 시간이 최소가 되게 자르는 게 핵심이다.

경계는 **"OS와 붙는 것 / 게임 안에서 도는 것"**으로 긋는다.

| | **갑 (심우진) — 플랫폼 레이어** | **을 — 게임 레이어** |
|---|---|---|
| 범위 | OS·Steam과 붙는 전부 | 게임 안에서 도는 전부 |
| 담당 | 오버레이 셸, 글로벌 입력, **커서 추종 창**, 트레이/자동시작, 저부하 최적화, 세이브 I/O, Steam SDK, 멀티 전송 계층, 빌드/업로드 | 코어 루프, 나무/원숭이 연출, 재화·상점·인벤토리·도감, 강화, 타수/레벨, UI 전반, **에셋 파이프라인**, 밸런싱 |
| 근거 | C++/네이티브·엔진 레벨 경험이 P/Invoke·윈도우 핸들링에 그대로 쓰인다. 프로젝트 최대 리스크 3개(커서·입력·저부하)가 여기 몰려 있다 | 게임 레이어는 리스크가 낮고 물량이 많다. 병렬로 계속 진도가 나가는 쪽 |
| 공동 | 기획·밸런스 결정, 세이브 스키마, 스팀 스토어 소재, QA, 마케팅 | |

### 8-2. 인터페이스 계약 (W1 Day 1에 시그니처만 먼저 고정)

**둘이 서로를 기다리지 않으려면 이게 먼저 있어야 한다.** 갑이 실물을 만드는 동안 을은 목(mock) 구현으로 게임 레이어를 돌린다.

```csharp
// 갑 제공 → 을 소비
interface IInputSource {
    event Action<int> OnKeystrokes;   // 100ms 배치, 캡 적용 후 개수
    long TotalCount { get; }
    bool IsAvailable { get; }         // false면 시간 기반 폴백으로 전환
}

interface ICursorLayer {
    void Equip(CursorSlot slot, string assetId);   // slot: Hang / Trail / Base
    void SetEnabled(bool on);
    bool IsSupported { get; }         // 커서 POC 실패 시 false
}

interface INetSession {
    Task<RoomHandle> CreateRoom();
    Task<RoomHandle> JoinRoom(string uid);
    void Broadcast(PlayerState s);    // 타건수, 수확 이벤트, 누적타수, 장착정보
    event Action<PeerId, PlayerState> OnPeerState;
    event Action<PeerId> OnPeerJoin, OnPeerLeave;
}

interface IShell {
    void SetScale(float s); void SetOpacity(float a);
    void SetClickThrough(bool on);
    Rect2I GetSafeArea();             // 멀티모니터 고려한 배치 가능 영역
}
```

**규칙**: 이 4개 인터페이스는 W1 Day 1에 파일로 커밋하고, 이후 변경은 상대에게 알린 뒤에만 한다. `IsAvailable` / `IsSupported` 플래그가 있는 이유는, 갑 쪽 스파이크가 실패해도 을이 멈추지 않게 하기 위해서다.

### 8-3. 협업 규칙

- 브랜치: `main` + 기능 브랜치. 서로의 담당 폴더는 건드리지 않는다 (`/platform`, `/game`, `/shared`)
- 매일 아침 15분 스탠드업. 어제 한 것 / 오늘 할 것 / 막힌 것만
- 주 1회(금요일) 데모 빌드 만들고 **둘 다 주말 동안 실제로 켜놓고 일한다.** 이 장르는 이게 유일한 진짜 QA다
- 추정이 1.5배를 넘어가면 그 자리에서 컷 논의. 혼자 끌지 않는다

## 10. 컷 라인 (자를 순서)

일정이 밀리면 **위에서부터 자른다.** 이 순서를 미리 합의해 두면 나중에 싸울 일이 없다.

1. 공동 나무 (W3 목요일 판정에서 이미 다룸)
2. 강화 시스템 (B13) → 1.1
3. 도감 화면 (B7) → 인벤토리 화면에 수집률 숫자만 표시
4. 커서 장식 16종 → 10종
5. 사운드 (B16) → 타건음 1종만
6. 멀티플레이 전체 → 1.1 (여기까지 오면 출시일을 미루는 게 낫다)

**절대 자르지 않는 것**: 코어 루프, 마이크로 피드백(B2), 커서 꾸미기, 옵션 화면, 저부하 최적화, 개인정보 문구, 스토어 소재.

마지막 세 개가 자주 잘리는데, 이 장르에서 저부하와 프라이버시 문구는 **기능이 아니라 신뢰 문제**다. 스팀 리뷰 한 줄에 프로젝트가 죽는다.

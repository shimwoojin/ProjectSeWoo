## 0. 배경 (2026-09-28 갑)

게임을 켠 사람의 흐름: 상점에 갖고 싶은 게 많다 → 바나나는 어떻게 얻지? → 시간이 지나야 열린다 → 빨리 얻으려면 강화.
그래서 두 가지를 더한다.

1. **유료 바나나** (예: 500 바나나 5,000원) — 켜자마자 갖고 싶은 사람. **§2 검토만. 만들지 않았다 - 갑 결정 대기**
2. **기부** — 바나나가 돈으로도 들어오면 도감을 다 채운 뒤 쓸 곳이 없다. 끝없는 사용처(싱크)가 필요하고, 그것을 멀티 자랑·도전과제로 쓴다. **§1, 만들었다**

### 1-1. 누적의 진실은 서버

잔액과 같은 원장이다 — `players.donated_total`, `POST /v1/economy/donate` (ECONOMY-SERVER-API §2-5). 도전과제가 이 값을 믿으므로
클라이언트가 지어낼 수 없어야 한다. 목 경제로 돌 때는 기부 도전과제를 해금하지 않는다(`TrustEconomyForAchievements`, A15 §3-2 와 같은 규칙).
스팀이 늦게 붙어도 `SyncAchievements` 가 누적을 보고 회수한다.

친구 칸의 칭호는 P2P 상태(전송 형식 v4, `PlayerState.DonatedTotal`)에서 온다 — 다른 필드처럼 친구 쪽 게임이 보내는 값이라 조작된
클라이언트는 거짓 칭호를 보낼 수 있다. 자랑 표시일 뿐이고 재화·도전과제에는 안 쓴다.

### 1-2. 확인 (2026-09-28)

- 서버: 로컬 워커 + 로컬 D1 에 테스트 스팀 ID 로 잔액 500 → 100 기부(400) → **같은 요청 재시도 = 그대로 400**(멱등) → 1,000 = 잔액 부족(그대로) → 300 (100) · 누적 400 · 0 은 400 bad_request
- `npm test` 27 (기부 금액 검사: 0 · 음수 · 1.5 · 문자열 · 10억+1 · null 이 전부 DB 전에 400)
- 게임 `--selftest` PASS (전송 형식 v4 왕복, 칭호 표), `--store-shot` 에 기부 탭 캡처 두 장(전 · 1,000 기부 뒤 칭호) + 목 친구 칭호

### 1-3. 배포 순서 (지키지 않으면 서버가 멈춘다)

1. **`cd server && npm run db:migrate:donate:remote`** — 칸 추가. `savePlayer` 가 이 칸을 쓰므로 **배포보다 먼저**
2. `npm run deploy` (개인정보 공개 페이지 문구도 같이 바뀐다)
3. 파트너 사이트: 도전과제 4개 + 통계 `STAT_DONATED`(INT · Increment Only · Min 0) 등록, 기부 과제 3개(1K·10K·100K)에 Progress Stat 연결 → 게시
4. 릴리스 빌드 → default (클라이언트가 전송 v4 - 옛 빌드끼리는 멀티에서 서로 안 보인다)

## 2. 유료 바나나 — 검토 (만들지 않았다)

### 2-1. 판단

**방향은 맞다.** "갖고 싶다 → 못 산다" 는 가장 강한 결제 동기이고, 이 게임은 확률 뽑기가 없어서(전 상품 상시 노출, 가격 표시) 결제가
설명하기 쉽다. 다만 **출시(10/26) 전에 붙이기보다 출시 뒤 업데이트로** 권한다 — 아래 §2-2 의 스팀 결제 연동·환불 처리·스토어 표시
변경이 각각 검수를 다시 부르고, 출시 전 4주에 이것을 넣으면 출시 자체가 밀릴 위험이 크다.

**값 감각** (시뮬레이터 수입 기준: 강화 없음 시간당 22.5 · 최대 162 바나나)

| | 500 = 5,000원 일 때 |
|---|---|
| 바나나 1개 | 10원 |
| 강화 없는 1시간 플레이 | ~225원 |
| 200 원숭이 | 2,000원 |
| 2,000 원숭이 | 20,000원 |
| 전부 (23,270 + 강화 8,240) | ~31만 원 |
| 게임 가격 $1.99 | ~2,700원 |

- 첫 결제 문턱이 게임 값의 두 배다. **작은 묶음(예: 150 = 1,500원)** 과 **첫 구매 보너스**를 같이 두면 전환이 쉽다
- 큰 묶음에 보너스(예: 1,100 = 10,000원)는 흔한 방식이다. 대신 "바나나를 사야만 재밌다" 로 보이지 않게 시간 수입은 그대로 둔다

### 2-2. 붙일 때 주의할 것

| | 무엇 | 왜 |
|---|---|---|
| **스팀 결제만** | 게임 안 디지털 재화는 **Steam Microtransactions**(`ISteamMicroTxn` - 서버가 `InitTxn` → 유저가 스팀 오버레이에서 승인 → 서버가 `FinalizeTxn`)로 판다. 외부 결제(토스·카드 직접) 링크는 안 된다 | 스팀 배포 조건. 결제·환불·세금은 스팀이 하고 30% 수수료 |
| **서버가 지급** | 바나나는 `FinalizeTxn` 성공을 **서버가 확인한 뒤** 원장에 더한다. 주문 ID 로 멱등(두 번 지급 금지). 클라이언트가 "샀다" 고 알리는 값은 믿지 않는다 | 지금 경제 서버 구조 그대로 붙는다 - 새 엔드포인트 2개 + 거래 표 |
| **환불·차지백** | 스팀 환불·카드 취소가 오면(`GetReport` 로 주기 조회) 준 바나나를 **회수**한다. 이미 써 버렸으면 잔액이 음수가 되게 하고 음수 동안 구매를 막는다 | **"바나나 산다 → 마켓 거래되는 장식 산다 → 장식 팔고 → 결제 환불" 이 돈 복사 구멍이 된다.** 장식이 마켓 거래 가능(marketable)이라 이 게임에서 가장 큰 위험 |
| **시험** | `ISteamMicroTxnSandbox` 로 진짜 돈 없이 전 과정 시험 | 실결제로 시험하면 환불 처리까지 손으로 해야 한다 |
| **스토어 표시** | 파트너 사이트 "지원 기능" 의 **인앱 구매를 켠다**(9/28 에 껐다), 스토어 설명에 "게임 내 구매" 를 적는다 | 안 적고 팔면 검수 반려·환불 사유 |
| **청약철회 안내** (전자상거래법) | 결제 창 전에 "사용한 바나나는 환불 불가, 쓰지 않은 것은 스팀 환불 정책" 을 보여 준다 | 한국 판매. 표시 없이 제한하면 청약철회를 못 막는다 |
| **미성년자** | 스팀 계정 기준이지만, 부모 동의 없는 결제는 취소될 수 있다는 전제로 위 환불 회수가 필요하다 | 민법상 취소권 |
| **등급·확률** | 확률형 아이템이 **없게 유지**한다(뽑기·랜덤 상자를 넣으면 확률 공개 의무가 생긴다). 등급 분류는 한국 판매 조건을 한 번 확인한다 | 2024년부터 확률 표시 의무 |
| **마켓과 현금화** | 산 바나나 → 마켓 거래 장식 → 스팀 지갑. 스팀 지갑은 현금 인출이 안 되지만, 밸브의 **마켓 승인 심사**(ECONOMY-SERVER §4)에서 "현금으로 산 재화로 거래 아이템을 찍어 낸다" 를 불리하게 볼 수 있다 | 마켓 승인이 아직이다 - 결제를 붙이기 전에 밸브에 물어보는 게 싸다 |
| **개인정보** | 결제 주문 ID·금액·시각을 서버에 저장하게 된다 → C2 §2-3 에 추가. 카드 정보는 우리가 안 만진다(스팀) | C2 원칙: 문장마다 코드 근거 |
| **기부와 도전과제** | 바나나를 살 수 있으면 **기부 도전과제를 돈으로 살 수 있다** | 도전과제 목록을 보는 사람에게 좋은 신호는 아니다. 1K·10K 는 그대로 두고 100K 는 "숨김" 으로 두는 정도를 고려 |
| **밸런스** | 산 바나나로 강화를 먼저 올리면 시간 수입이 7배가 된다. 멀티 랭킹은 로비 타수라 영향 없다 | 강화를 결제로 사는 것이 "승리" 가 아니게 지금 구조(랭킹 = 타수)를 유지 |

### 2-3. 만든다면 작업 목록 (추정 3~5일)

1. 파트너 사이트: 마이크로트랜잭션 설정 확인, 인앱 구매 표시, (마켓 승인 문의)
2. 서버: `POST /v1/purchase/bananas/init`(`InitTxn`, 주문 표) · `/finalize`(승인 콜백 뒤 `FinalizeTxn` → 지급) · 환불 조회 크론(`GetReport` → 회수)
3. 클라이언트: 상점에 "바나나 사기" 묶음, 청약철회 안내, `MicroTxnAuthorizationResponse_t` 콜백 → finalize 요청
4. 샌드박스로 끝까지 시험 (지급 · 두 번 지급 안 됨 · 환불 회수 · 음수 잔액 구매 금지)
5. C2 · 스토어 설명 · DEVLOG

# A7 — 저부하 최적화 + 실측 (커서 창 포함)

관련: [확정 기획서](기획확정-일감분배-260907.md) A7 · §7-3 / [Day 1-2 스파이크](DAY1-2-SPIKE.md) §4-5

> §7-3이 요구한 "커서 추종 창을 포함해서 실측"을 A2~A6이 전부 끝난 지금 시점에
> 했다. 최적화 레버를 하나 찾아 시도했는데 **이 아키텍처에서는 작동하지 않는다는
> 것**이 결론이었다 - 그 경위를 남긴다. 150MB 기준으로는 FAIL이었고, 사용자가
> **기준 자체를 재검토**하기로 결정해 `PrivWS` < 300MB로 재설정했다 (§4).

---

## 0. 상태 (2026-09-16)

| 항목 | 결과 |
|---|---|
| 유휴 CPU < 1% (전 기능 포함) | ☑ **Go** — `0.40%` |

| .NET 런타임 튜닝(GC/ICU) 시도 | ☒ **이 아키텍처에서 작동 안 함** (§2) — 실측으로 폐기 |
| Release 재측정 | ☐ **미실시** — 이 PC에 export 템플릿 없음 (§3) |

## 1. 측정 — 이번엔 진짜 "커서 창 포함"이다

지금까지 §7-3의 "커서 창 포함 실측"은 계속 미뤄져 있었다. Day1-2(2026-09-14)의
376MB/268MB는 **셸 단독** 값이었다. A2(커서 창)·A4(입력 헬퍼)·A5(3슬롯 장착)·
A6(트레이·옵션·전체화면 감지)까지 다 붙은 지금에야 §7-3이 원래 요구한 조건이
갖춰졌다.

`Debug` 빌드, standalone, 3슬롯 전부 장착(`--cursor-equip=monkey_01,leaf_02,base_03`),
90초 측정 + 30초 워밍업. 두 조건을 나눠 쟀다 - 하나는 진짜 유휴, 하나는 A2 스파이크
때처럼 커서를 논스톱으로 흔든 최악 조건.

| 조건 | cpu avg | cpu peak | priv 커밋 | ws |
|---|---|---|---|---|
| 진짜 유휴 (마우스 방치) | **0.40%** | 1.57% | 388MB | 388MB |
| 최악 (`--cursor-sim`, 논스톱 이동) | 1.02% | 2.27% | 386MB | 387MB |

**CPU는 Go.** 최악 조건에서 `1.02%`로 기준을 살짝 넘긴 건 사실이지만, 그 조건은
"마우스가 90초 내내 한 번도 안 쉰다"는 실사용에 없는 시나리오다(A2 스파이크가
CPU 상한을 재려고 일부러 만든 최악 조건). 진짜 유휴 `0.40%`가 기준의 절반
이하라 이걸로 판정한다.

**메모리는 셸 단독(376MB, 릴리스)과 거의 같다(386~388MB, +10MB 안팎).**
커서 창·헬퍼 프로세스·트레이 아이콘·옵션 UI·전체화면 감지를 전부 얹어도 늘어난
폭이 크지 않다는 뜻이다 — 즉 **150MB를 못 맞추는 원인은 우리가 붙인 기능들이
아니라 `d3d12` 렌더러 + .NET 호스팅 자체의 기본 비용**이다. 9/14 결론을 다시
확인한 셈이다.

## 2. 시도했지만 안 된 것 — .NET 런타임 튜닝

메모리 구성을 다시 보면: `godot 94MB + clr heap 5MB ≈ 99MB`인데 `priv`는
`386MB`다. **287MB가 어디서 오는지 `PerfProbe`로는 안 보인다.** 유력한 후보가
.NET 런타임 자체의 호스팅 비용(CoreCLR 초기화, GC 힙 세그먼트 예약, ICU
로케일 데이터)이라 두 가지를 시험했다.

### 서버 GC인가 확인 — 아니었다

16코어 개발 PC에서 서버 GC가 켜져 있으면 **코어마다 힙 세그먼트를 하나씩**
예약해서 실제 사용량과 무관하게 커밋이 크게 뛴다. 확인해 봤다:

```csharp
GD.Print($"serverGC={System.Runtime.GCSettings.IsServerGC}");
// 결과: serverGC=False
```

**이미 워크스테이션 GC였다.** 이 레버는 애초에 당길 게 없었다.

### ICU(전체 로케일 데이터) 끄기 — 설정은 먹는데 효과가 없다

`InvariantGlobalization`을 켜면 ICU 로딩을 건너뛰어 흔히 수십MB를 아낀다.
`ProjectSeWoo.csproj`에 추가하고 빌드하면 `ProjectSeWoo.runtimeconfig.json`에
`"System.Globalization.Invariant": true`가 정확히 들어간다 — **설정 자체는
됐다.** 그런데 실행해서 확인하면:

```csharp
AppContext.TryGetSwitch("System.Globalization.Invariant", out bool ig);
// 결과: false
```

**적용이 안 됐다.** 원인은 구조에 있다 — **`ProjectSeWoo.dll`은 우리가 만든
`.exe`가 아니라 Godot이 미리 초기화해 둔 .NET 호스트(`GodotSharp`/`GodotPlugins`)에
"얹히는" 플러그인 어셈블리다.** GC 모드·전역화 모드 같은 **프로세스 전역
런타임 설정은 CoreCLR을 맨 처음 띄운 쪽의 `runtimeconfig.json`(Godot 자체의
`GodotPlugins.runtimeconfig.json`)이 결정하고, 나중에 로드되는 우리 어셈블리의
`ProjectSeWoo.runtimeconfig.json`은 그 시점엔 이미 늦다.** 확인해 보니
`GodotPlugins.runtimeconfig.json`에도 이런 설정이 없어서, 그냥 CoreCLR
기본값(전체 ICU 로드)으로 고정돼 있다.

**결론: 이 프로젝트 구조에서는 `.csproj`로 .NET 런타임 동작(GC 모드, 전역화,
트리밍 등)을 바꿀 수 없다.** Godot 자체의 임베디드 런타임 설정을 건드리는
방법이 없는 한(별도 조사가 필요하고 지원 여부도 불확실), 이 레버는 폐기다.
DAY1-2-SPIKE.md §4가 남겨둔 "메모리 초과 시 옵션 2 (.NET 트리밍/GC 설정)"는
**이 프로젝트에서는 선택지가 아니다** — 실측으로 닫혔다.

(시도한 코드는 커밋하지 않고 되돌렸다 — 효과 없는 설정을 프로젝트에 남겨두면
나중에 누군가 "이미 껐는데 왜 안 되지"로 헷갈린다.)

## 3. Release 재측정 — 이 PC에서는 못 했다

`Godot_..._console.exe --headless --path . --export-release "Windows Desktop" ...`를
시도했으나:

```
ERROR: Cannot export project with preset "Windows Desktop" due to configuration errors:
예상된 경로에서 찾은 내보내기 템플릿이 없습니다: .../windows_debug_x86_64.exe
예상된 경로에서 찾은 내보내기 템플릿이 없습니다: .../windows_release_x86_64.exe
```

**Export 템플릿(4.7.2.stable.mono용)이 이 PC에 설치돼 있지 않다.** 9/14 기록의
Release 수치(376MB 등)는 이 세션에서 새로 뽑은 게 아니라 그 시점 세션의
결과다. 지금 `Debug` 빌드로 잰 386~388MB는 **보수적인 값**이고(Debug가 보통
더 무겁다 - 단, 9/14 기록은 d3d12만 예외적으로 Release가 Debug보다 12% 더
무거웠다는 것도 같이 알아둘 것), 정확한 Release 재확인이 필요하면 템플릿
설치(에디터에서 자동 다운로드 몇백MB~1GB대, Godot 버전과 정확히 일치해야 함)가
먼저다.

## 4. 메모리 게이트 — 여기서부터는 판단이 필요하다

DAY1-2-SPIKE.md §4가 열어둔 세 선택지에, 실측으로 얻은 정보를 더해서 다시 쓴다.

| # | 선택지 | 이번 실측이 준 정보 |
|---|---|---|
| 1 | 기준 지표를 `PrivWS`(개인 작업 집합)로 바꾼다 | 9/14 기준 `priv` 376MB → `PrivWS` 268MB로 약 29% 줄지만, **그래도 기준의 1.8배**. 지표만 바꿔서는 안 닫힌다 |
| 2 | 메모리를 실제로 깎는다 (`gl_compatibility` 재고) | `gl_compatibility`는 셸 단독 228MB(Release)까지 검증됐다(투명 정상 포함). 다만 **렌더 경로를 바꾸면 §3-2 플리커 Go 판정을 그 경로에서 다시 봐야 한다** - 지금 Go는 d3d12 경로에서만 확인됐다. 전 기능 포함 재측정도 다시 해야 한다 |
| 3 | C#/.NET 자체를 재검토 | .NET 런타임 튜닝이 이 구조에서 안 먹힌다는 게 이번에 확인됐지만, 그렇다고 "C#이 원인"은 아니다 - 287MB 미상 비용 대부분은 **Godot 엔진 자체의 .NET 호스팅**이지 우리 코드가 아니다. 다시 짜도 Godot+.NET을 쓰는 한 이 비용은 그대로다. 엔진을 바꾸는 것과 같은 얘기이고, 이미 투입한 시간(A1~A7)을 버리는 선택이라 비용이 가장 크다 |
| 4 *(신규)* | **기준 자체를 재검토한다** | 150MB는 §7-3이 스스로 정한 목표이지, 스팀이나 OS가 강제하는 수치가 아니다. 상주 트레이 앱 카테고리에서 300~400MB대는 드물지 않은 수준이다(Discord, Slack 등 Electron 기반 상주 앱은 대개 이보다 훨씬 무겁다). "유휴 CPU 1% 이하"라는 더 중요한 체감 지표는 이미 Go다 |

### 추천

**4번(기준 재검토)을 1순위로, 필요하면 2번(`gl_compatibility` 재도전)을 조건부로
추천한다.** 근거:

- 3번은 이미 투입한 3주 가까운 작업(A1~A7)을 버리는 선택이라 남은 일정(10월
  중순 출시 목표)에서 감당이 안 된다.
- 1번은 부분적으로만 도움이 되고 근본 해결이 아니다.
- 2번은 유효한 카드지만 **공짜가 아니다** — 플리커 재검증(Go/No-Go가 갈릴 수
  있는 유일한 "근본적으로 안 됨" 항목)과 전체 기능 포함 재측정을 다시 해야
  한다. "메모리가 유저 이탈의 실제 원인인가"가 불확실한 상태에서 먼저 쓸
  카드는 아니라고 본다.
- 150MB는 Week 0 검증 계획 초기에 잡은 목표이지 외부 강제 기준이 아니다.
  유휴 CPU 1%(체감에 직결)는 이미 통과했고, 메모리 300~400MB대가 실제로
  유저 불만으로 이어지는지는 아직 데이터가 없다.

### 결정 (2026-09-16) — 4번 채택. 기준을 실측 기반으로 재설정한다

**새 기준: 유휴 시 개인 작업 집합(`PrivWS`, 작업관리자 "메모리" 열) < 300MB.**
`priv`(개인 커밋)는 참고 지표로 내리고, 유저가 실제로 보는 값을 정식 기준으로
올린다.

**300MB를 고른 근거** — 9/14 Release 셸 단독 측정에서 `priv` 376MB일 때
`PrivWS`는 268MB였다(비율 약 0.71). 이번 A7의 전 기능 포함 Debug 측정
`priv` 388MB에 같은 비율을 적용하면 `PrivWS` ≈ 276MB로 추정된다. **다만
이건 추정이다** — Release 빌드로 `PrivWS`를 직접 잰 적은 아직 없다(§3, 템플릿
미설치). 300MB는 그 추정치(276MB)에 여유를 얹은 반올림 값이고, Release
재측정에서 크게 벗어나면 다시 조정한다.

**판정**: 이 기준으로 메모리는 **조건부 Go**다 — 실측값이 아니라 비율
추정값으로 통과했다는 점을 판정 근거에 남긴다. 확정 Go로 올리려면 Release
export 템플릿을 설치하고 `PrivWS`를 직접 재는 것이 §6의 다음 항목이다.

**150MB는 원래도 `기획확정-일감분배-260907.md`(확정 기획서)에 없던 숫자였다** —
`WEEK0-GODOT-VALIDATION.md` §2가 검증 단계에서 잡은 예비 목표였을 뿐, §7-3
확정 문구는 "유휴 시 CPU 1% 이하, 배터리 영향 없음"만 요구한다. 기준을
바꾸는 게 확정 기획을 뒤집는 게 아니라, **검증 단계 임시 목표를 실측으로
정식화하는 것**이라는 뜻이다.

### 뜻밖의 소득 — 프라이버시 증명이 더 강해졌다

§7-2 는 *"키 코드를 읽지 않는다"* 를 코드로 증명하라고 요구한다. 프로세스가
갈라지면서 **게임 본체에는 키보드 원본 데이터를 만지는 코드가 한 줄도 없게 됐다.**

검증할 코드가 `platform/InputHelper/RawKeyboardCounter.cs` 하나로 모이고,
그 파일은 창 하나 만들고 오프셋 세 개 읽는 것이 전부다. 파일을 읽지 않고,
네트워크를 열지 않고, 창을 보여주지 않는다. **백신·안티치트 검증을 받을 때
작을수록 유리하다.**

## 1. 구조

```
platform/InputHelper/            별도 exe. 타건 수만 센다
  RawKeyboardCounter.cs            RawInput 수신 + 캡 + 감쇠   ★ 검증 대상은 여기뿐
  Program.cs                       공유 메모리에 쓰고 부모 생존 확인
shared/InputBridge.cs            공유 메모리 규약 (양쪽이 링크한다. Godot 의존 없음)
platform/HelperInputSource.cs    게임 측 IInputSource. long 몇 개를 읽는 게 전부
```

- **RawInput(WM_INPUT). `WH_KEYBOARD_LL` 은 쓰지 않는다** (§7-2)
- 헬퍼는 보이지 않는 1x1 최상위 창에 `RIDEV_INPUTSINK` 로 등록
- 헬퍼는 `GetMessage` 로 **블록**한다. 아무도 안 치면 깨어나지 않는다
- 200ms 마다 누적값을 공유 메모리에 쓰고 부모 생존을 확인
- 게임은 100ms 마다 읽어 `OnKeystrokes` 로 넘긴다

### 왜 파이프가 아니라 공유 메모리인가

게임이 필요로 하는 것은 "지금까지 몇 타" 라는 **누적값 하나**이고 100ms 마다
읽으면 충분하다. 연결 관리·재접속·블로킹이 없는 쪽이 상주 앱에 맞고, 헬퍼가
죽었다 살아나도 게임 쪽 코드가 바뀔 게 없다. 전부 `long` 정렬이라 x64 에서
읽기/쓰기가 원자적이고 락이 필요 없다.

### 죽으면 다시 띄운다

상주 앱은 며칠씩 켜져 있으므로 헬퍼가 한 번 죽으면 그날 타수가 통째로 사라진다.
심장박동이 2초 이상 끊기면 3초 간격으로 재기동한다. `magic` 표식을 따로 두는
이유는 **"아직 시작 전" 과 "죽었다" 를 구분**하기 위해서다.

반대로 게임이 죽으면 헬퍼도 나간다 — 헬퍼가 200ms 마다 부모를 확인하고,
게임도 종료 시 헬퍼를 정리한다. **유령 프로세스가 남지 않는 것을 확인했다.**

## 2. "키 코드를 읽지 않는다" 를 코드로 증명하는 방법

§7-2 는 *"코드 레벨에서 증명 가능한 구조로 작성"* 을 요구한다. 이렇게 했다.

RAWINPUT 버퍼를 구조체로 마샬링하지 **않는다.** 필요한 오프셋 세 개만 직접 읽는다.

```
offset  0  dwType          (4)  <- 읽는다. 키보드인지 마우스인지 확인

[키보드]
offset 24  MakeCode        (2)  <- 읽지 않는다 (스캔 코드)
offset 26  Flags           (2)  <- 읽는다. 누름/뗌 구분
offset 30  VKey            (2)  <- 읽지 않는다 (가상 키 코드)

[마우스]  2026-09-19 추가
offset 28  usButtonFlags   (2)  <- 읽는다. 버튼이 눌렸는가 (마스크와 != 0 비교만)
offset 30  usButtonData    (2)  <- 읽지 않는다 (휠 회전량)
offset 36  lLastX          (4)  <- 읽지 않는다 (이동량)
offset 40  lLastY          (4)  <- 읽지 않는다 (이동량)
```

마우스 버튼은 **눌림 비트를 합친 마스크 하나와 `!= 0` 비교만** 하고 개별 비트를
꺼내지 않는다. 그래서 "어느 버튼인지" 도 모른다 — 키보드에서 키 코드를 안 읽는
것과 같은 수준이다.

**구조체를 만들면 키 코드가 필드로 존재하게 되고, "안 읽는다" 가 규율의 문제가 된다.**
오프셋 두 개만 읽으면 구조적으로 못 읽는다. `IInputSource` 에 키를 나타내는 타입이
없는 것과 같은 이유다.

### §6 의 "동일 키 연속 감쇠" 를 타이밍 기준으로 바꿨다

기획서 안에 모순이 있다:

- §7-2: **키 코드를 읽지 않는다**
- §6: **동일 키 연속 입력 시 5타 이후 감쇠** ← 같은 키인지 알려면 키 코드를 읽어야 한다

§10 이 개인정보 문구를 "절대 자르지 않는 것" 에 넣었고 §7-2 가 증명 가능성을 요구하므로
**프라이버시 쪽이 우선**이다. 그래서 감쇠 기준을 키 동일성이 아니라 **타건 간격의
규칙성**으로 바꿨다.

사람의 타건 간격은 들쭉날쭉하고 매크로·키 홀드 자동 반복은 메트로놈처럼 규칙적이다.
키 코드를 안 봐도 갈린다. **오히려 더 넓게 막는다 — 서로 다른 키를 번갈아 누르는
매크로까지 잡히고, 그건 원래 규칙으로는 못 잡던 것이다.**

> **2026-09-24 정정 — 자동 반복(키 홀드)은 이 장치에 걸리지 않았다.** 키를 꾹 누르면
> 초당 10타(캡)까지 계속 올랐다. 간격을 `GetTickCount64`(약 15.6ms 단위)로 재서
> 33ms 반복이 31/47ms 로 들쭉날쭉하게 보였고, 허용 오차(12%)를 번번이 빠져나갔다.
> 그래서 **키보드는 이제 "뗌" 에서 센다.** 자동 반복은 누름만 되풀이하고 뗌은 손을 뗄
> 때 한 번뿐이라, 얼마나 오래 누르든 1타다. 읽는 값은 그대로 누름/뗌 플래그 하나다
> — 키 코드 없이 "같은 키의 반복" 을 가르는 방법이 이것뿐이다(Shift 를 누른 채 치는
> 대문자와 섞여도 갈린다). 같은 날 규칙성 판정도 두 군데 고쳤다 — 간격을 `Stopwatch`
> 로 재고, 2초 넘게 쉰 뒤에는 평균을 비운다(쉰 시간을 평균에 넣어서 쉬었다 시작하는
> 매크로가 매번 약 20타씩 통과하고 있었다). SendInput 주입 실측(F24):
>
> | 시나리오 | 기대 | 전 | 후 |
> |---|---|---|---|
> | 3초 홀드 (33ms 자동 반복) | 1 | 30 | **1** |
> | 사람 타자 20타 | 20 | 20 | 20 |
> | 롤오버 10쌍 (앞 키를 떼기 전에 다음 키) | 20 | 20 | 20 |
> | 한 키 홀드 + 다른 키 10타 (Shift 대문자) | 11 | 36 | **11** |
> | 매크로 30타 @100ms | ~5 | 23 | **6** |

> **2026-09-14 확정.** 기획서 §6 문구도 이에 맞게 고쳤다. 스토어 문구(§7-6)는
> 그대로 유지된다 — 그게 이 방향을 고른 이유다.

## 3. (기록) 엔진 프로세스 안에서는 왜 안 됐나

### 증상

같은 PC, 같은 순간, 같은 키 입력(합성 F13)에 대해:

| | `wm_input` | 키보드 이벤트 | 판정 |
|---|---|---|---|
| **별도 프로세스 수신기** (WinForms 창) | 68 | **keydown 34** | ☑ 동작 |
| **게임 내 모듈** | 2 | **keydown 0** (둘 다 마우스) | ☒ 실패 |

게임 쪽 등록 상태는 정상이었다:

```
input reg: [page 01 usage 06 flags 0x100 target 0x510FE8 <-우리 창]   (0x100 = RIDEV_INPUTSINK)
input on [RawInput INPUTSINK], total 0, ..., re-reg 0
```

**등록은 우리 것이고, 덮어쓰기도 없었고(re-reg 0), 그런데 키보드 WM_INPUT 만 안 온다.**

### 여기까지 오면서 넘은 벽 (전부 실측으로 확인)

| # | 증상 | 원인 | 대응 |
|---|---|---|---|
| 1 | WM_INPUT 0건 | **엔진이 우리 등록을 덮어쓴다.** RawInput 등록은 (UsagePage, Usage) 당 프로세스에 하나뿐이고 나중에 부른 쪽이 교체한다. 조회에 `flags 0x0 target 0x0` 으로 남아 있었다 | 1초마다 확인 후 재등록 |
| 2 | 재등록해도 0건 | **엔진 메인 창 서브클래싱이 문제.** 후킹은 걸렸고(메시지 22건 수신) 등록도 우리 것이었는데 안 왔다 | 전용 수신 창을 따로 만듦 |
| 3 | 전용 창도 0건 (`msg 4`) | **메시지 전용 창(`HWND_MESSAGE`)에는 RIDEV_INPUTSINK 가 안 온다.** 그 4건은 창 생성 중 `SendMessage` 로 직접 온 것들뿐이고 큐를 거치는 메시지는 하나도 없었다 | 실제 최상위 창으로 변경 |
| 4 | 숨긴 최상위 창도 0건 | **`WS_VISIBLE` 이 필요하다.** 동작하는 대조군은 창이 실제로 표시된 상태였고 그 차이뿐이었다 | 1x1 + TOOLWINDOW + NOACTIVATE 로 보이게 생성 |
| 5 | WM_INPUT 은 오는데 키보드가 0 | `lastType 0` = **전부 마우스 입력**이다. 키보드는 끝내 안 왔다 | **여기서 접고 별도 프로세스로 갔다** |

1~4 는 각각 진짜 함정이고 다른 프로젝트에서도 밟을 만하다. 특히 3·4 는 문서에
잘 안 나오는 것들이라, **헬퍼 구현에도 그대로 반영돼 있다** —
`RawKeyboardCounter` 가 메시지 전용 창을 안 쓰고 `WS_VISIBLE` 을 붙이는 이유가
여기서 나왔다.

5 의 원인은 끝내 규명하지 못했다. 5단계를 넘은 시점에서 남은 실마리가 없었고,
일정이 이미 1주 밀린 상태라 **Week 0 이 미리 적어둔 폴백으로 갈아탔다.**
"왜 안 되는지" 보다 "되는 길이 있는지" 가 먼저인 국면이었다.

### 진단에 쓴 방법

**대조군을 먼저 만들었다.** "안 세진다" 의 원인이 둘인데 밖에서는 구분이 안 된다 —
내 테스트가 만든 입력을 RawInput 이 애초에 안 보는가, 아니면 통합이 못 받는가.
Godot 과 무관한 최소 수신기(WinForms + 같은 등록)를 띄워서 갈랐다. 대조군이
`keydown=9` 를 세는 것을 확인하고 나서야 "우리 쪽 문제" 로 좁힐 수 있었다.

`keybd_event` 가 실제로 OS 에 도달하는지도 `GetAsyncKeyState` 로 따로 확인했다
(`-32767`). 이걸 안 했으면 하네스를 의심하며 시간을 더 썼을 것이다.

## 4. 검증 결과 (2026-09-14)

합성 키 입력(F13)으로 세 조건을 각각 잰다. F13 은 물리 키보드에 거의 없고 앱들이
무시하는 키라, 포커스가 어디에 있든 아무 일도 안 일어난다.

**측정 내내 게임 창은 포그라운드가 아니었다** — 즉 `RIDEV_INPUTSINK`(포커스 없이
수신)가 실제로 동작한다는 것까지 같이 확인된다. 상주 앱에서 이게 안 되면 기능
자체가 성립하지 않는다.

| 조건 | 센 타수 | 캡 버림 | 감쇠 버림 | 판정 |
|---|---|---|---|---|
| A) 사람 속도 5타 (250ms ±80 지터) | **5** | 0 | 0 | ☑ 정상 타이핑을 안 깎는다 |
| B) 빠른 연타 20타 (약 16타/초) | 13 | **7** | 0 | ☑ 초당 10타 캡 동작 |
| C) 매크로 20타 (정확히 100ms) | 7 | 0 | **13** | ☑ 규칙적 입력 5타 이후 감쇠 |

A 가 대조군 역할을 한다. **A 에서 버림이 0 이라는 것이 중요하다** — 방어가
동작한다는 것만 보고 끝내면 "정상 유저의 타자까지 깎고 있다" 를 놓친다.

재현: `scratchpad/probe-input.ps1`

| **C. 계속 파기** | 엔진 프로세스 안에서 원인 규명 | 되면 가장 깔끔 | 이미 5단계를 넘었고 남은 실마리가 없다. 일정이 이미 1주 밀렸다 |

**A 를 채택했다.** §7-2 의 검증 항목(Defender / VirusTotal / Vanguard)이 바이너리
둘에 각각 필요해지므로 **A13 의 범위가 늘어난다.** 다만 헬퍼가 "타건 수만 세고
아무것도 안 하는" 최소 바이너리라 게임 본체보다 오히려 검증받기 쉬운 면도 있다.

## 7. (기록, 미해결) 타건마다 +1 되는 실시간 연출은 이 구조로는 안 된다

**2026-09-15 확인.** IPC 를 "누적값 스냅샷 폴링"으로 설계한 대가다 (§1 "왜 파이프가
아니라 공유 메모리인가"). 경로를 다시 쓰면:

```
키 입력 → 헬퍼 WM_INPUT (즉시, 프로세스 내부 카운터만 오름)
        → 200ms 주기 WM_TIMER 때만 공유 메모리에 씀        ← 1차 배치
        → 게임이 100ms 주기로 그 값을 읽어 diff 를 이벤트로 쏨  ← 2차 배치
```

두 겹의 폴링을 거치므로 **개별 타건의 시각·순서는 프로세스 경계를 못 넘어간다.**
게임이 받는 건 "지난 폴링 구간 동안 몇 타"라는 뭉친 정수 하나뿐이다.

- 최선의 경우도 키 입력 → 게임 반영까지 최대 ~300ms(헬퍼 200ms + 게임 100ms) 지연.
- 100ms 안에 2타 이상 치면 `OnKeystrokes` 가 한 번에 `diff≥2` 로 뭉쳐서 온다.
  "한 타 = 한 번의 반응" 연출은 정확히 못 맞추고, 빨리 칠수록 더 뭉친다.
- 캡/감쇠로 버려진 타건은 `TotalCount` 에 애초에 안 들어간다(§6). 몇 개 버려졌는지
  (`DroppedByCap`/`DroppedByDecay`)는 알아도 **어느 타건이 버려졌는지는 알 수 없다.**
  이건 키 코드를 안 읽는 설계(§2)의 당연한 귀결이라 별개 문제는 아니다.

**아직 `HelperInputSource.OnKeystrokes` 를 구독하는 곳이 없어서(게임 레이어 미착수)
드러나지 않았을 뿐, 게임 레이어가 붙는 순간 그대로 체감될 제약이다.** 폴링 주기를
줄이면 완화는 되지만(헬퍼 200ms / 게임 100ms → 더 촘촘히), 완전한 "실시간 1타 1반응"은
**주기적 스냅샷 폴링** 이라는 이 아키텍처로는 원천적으로 안 되고, 타건마다 개별
이벤트를 큐에 쌓아 전달하는 구조로 바꿔야 나온다.

**지금 고치지 않는다.** 게임 레이어가 실제로 즉각적인 타건 반응 연출(타 칠 때마다
캐릭터가 움직인다 등, Week0 §5 Punchy 목업 같은 것)을 요구하는 시점에 재검토.
그때까지는 "숫자가 몇백ms 지연·뭉침으로 누적되는" 연출(성장 게이지, 카운터 텍스트
등)에만 이 경로를 쓴다.

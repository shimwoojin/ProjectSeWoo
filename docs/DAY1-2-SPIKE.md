## 0. 준비 — Godot .NET(mono) 빌드 받기 ★필수★

지금 `~/Downloads`에 있는 건 **표준 빌드**(`Godot_v4.7.2-stable_win64.exe`)라 C#을 못 읽는다.
[godotengine.org/download/windows](https://godotengine.org/download/windows) 에서 **`Godot_v4.7.2-stable_mono_win64.zip`** 을 받아 압축을 풀고, 그 안의 `Godot_v4.7.2-stable_mono_win64.exe`로 프로젝트를 연다.

- 표준 빌드는 단일 exe, mono 빌드는 **폴더째**다. exe만 빼내면 실행되지 않는다.
- .NET SDK는 이미 설치돼 있다 (9.0.301). .NET 8 런타임(8.0.17)도 있어서 `net8.0` 타깃이 그대로 돈다.
- 에디터 없이 컴파일만 확인하려면: `dotnet build ProjectSeWoo.csproj`

## 3. 측정 순서

### 3-1. 유휴 부하 (합격 기준: CPU < 1%, 메모리 < 150MB)

**측정은 반드시 standalone 실행으로 한다. VS F5 금지.** 디버거가 붙으면 JIT 최적화가 일부
꺼지고 오버헤드가 붙어 CPU/메모리 숫자가 모두 틀어진다. 그리고 **Godot 에디터를 닫는다.**
안 닫으면 프로세스 목록에 `Godot_v4.7.2-stable_mono_win64.exe`가 두 개 떠서 어느 쪽이
게임인지 구분이 안 된다.

측정 전 HUD가 출하 설정인지 확인한다: `pass on`, `cap 60`, `lowpower on`.

1. 실행 후 30초 대기 → 메모리 값을 적어둔다 (메모리는 30~60초에 안정된다)
2. 몸통을 한 번 클릭해 포커스를 주고 `F10`으로 리셋
3. **손대지 말고 10분 방치** (HUD의 `up` 값이 600초가 될 때까지)
4. `F9` → 클립보드 → 기록표에 붙여넣기
5. 1번의 30초 값과 10분 값의 `priv`를 비교한다. 수십 MB 늘어나면 **누수**다.
   상주 앱에서 누수는 CPU보다 치명적이므로 이 비교를 건너뛰지 않는다.
6. 필요하면 `F5`로 FPS 캡을 30, 10으로 바꿔가며 반복. 단 1번 조건(저전력 on / 캡 60)이
   통과하면 나머지는 판정에 필요하지 않다

CPU는 HUD의 `cpu avg`로 판정한다. `peak`는 클릭/드래그 순간 부하라 1%를 넘어도 된다.

#### 메모리는 숫자가 세 개이고 서로 다르다

지표를 잘못 고르면 판정이 뒤집힌다. 실제로 첫 측정에서 이 실수를 했다.

| 숫자 | 성격 | HUD | 작업관리자 |
|---|---|---|---|
| 전체 작업 집합 | 물리 RAM 점유. **공유 DLL 페이지 포함** → 과대평가 | `ws` | — |
| 개인 커밋 | 이 프로세스만 책임지는 커밋. **판정 기준으로 쓴다** | `priv` | `커밋 크기` |
| 개인 작업 집합 | 물리 RAM 중 우리만 쓰는 부분. **유저가 보는 값** | — | `메모리`(기본 열) |

대체로 `개인 작업 집합` <= `개인 커밋(priv)` <= `ws` 이므로, `priv`로 판정하면 보수적이다.
D3D12 런타임 / GPU 드라이버 / .NET 런타임의 DLL 페이지가 `ws`에 다 들어가기 때문에
`ws`를 150MB 기준에 대면 안 된다.

#### 세 숫자를 한 번에 뽑는 명령

Windows 11 작업관리자에서 `커밋 크기` 열을 추가하려면 `세부 정보` 탭에서 열 머리글 우클릭 →
`열 선택` → 목록에서 찾아야 하는데 번거롭다. PowerShell 한 줄이 더 확실하다.

```powershell
Get-CimInstance Win32_PerfFormattedData_PerfProc_Process -Filter "Name LIKE 'Godot%'" |
  Select-Object Name, IDProcess,
    @{n='PrivWS_MB';e={[int]($_.WorkingSetPrivate/1MB)}},
    @{n='WS_MB';e={[int]($_.WorkingSet/1MB)}},
    @{n='PrivCommit_MB';e={[int]($_.PrivateBytes/1MB)}}
```

`PrivCommit_MB`가 HUD의 `priv`와 일치해야 한다. 크게 다르면 `PerfProbe`가 틀린 것이니
그것부터 잡는다. `PrivWS_MB`가 유저가 작업관리자에서 보는 값이다.
(리소스 모니터 `resmon` → `메모리` 탭에서도 프로세스별 `커밋` / `작업 집합` / `개인`을 볼 수 있다)

### 3-2. 플리커 재현 (godot#80098)

**무엇을 보는 것인가** — 투명 창 + `window_set_mouse_passthrough` 조합에서 창이 흰색으로
깜빡인다는 리포트다. 마스코트가 아니라 **투명해야 할 영역**을 본다. 불투명한 사각형이
한 순간 번쩍이거나, 창 전체가 한 프레임 날았다가 돌아오거나, 테두리가 지글거리는 것.

`writes` 카운터 차이는 **대조군일 뿐 결과가 아니다.** "F3 토글이 실제로 동작한다"를
확인하는 것이고, 판정은 눈으로 본 화면이다.

1. **`F2`로 passthrough를 켠다. HUD에 `pass on` 확인 ★필수★**
   껐으면 매 프레임 *빈 폴리곤*을 쓰는 것이라(`OverlayShell.BuildRegion`) 재현 조건이 아니다
2. `F5`로 FPS 캡을 `none`(무제한)까지 올린다 → 쓰기 빈도 최대 = 최악 조건
3. 창 뒤에 **어두운 배경과 밝은 배경을 둘 다** 써본다
   - 어두운 배경(어두운 배경화면, 다크모드 창) → **흰색** 번쩍임이 드러난다
   - 밝은 배경(메모장 새 문서) → **검은색** 번쩍임이 드러난다
   - 아티팩트가 어느 색인지 모르므로 한쪽만 보면 놓친다
4. `F3` → `every-frame`으로 1~2분 관찰. 가만히 두고도 보고, **창을 드래그해 배경 위를
   지나가면서도** 본다
5. `F3` → `on-change`로 되돌려 같은 조건에서 관찰
6. 끝나면 `F5`로 캡 60 복구

> 육안으로 안 보이면 `Win`+`Alt`+`R`(게임 바)로 30초 녹화해서 한 프레임씩 넘겨본다.
> 고주사율 모니터에서는 한 프레임 아티팩트가 수 ms라 놓치기 쉽다.

| 결과 | 의미 |
|---|---|
| every-frame에서만 깜빡임 | **회피책이 통한다.** 폴리곤을 상태 변화 시에만 갱신하면 됨 → Go |
| 둘 다 깜빡임 | Godot 자체 문제. 창 크기를 고정하고 폴리곤을 아예 안 바꾸는 설계로 갈지 판단 필요 |
| 둘 다 안 깜빡임 | 4.7.2에서 수정됐다. 그대로 진행 |

세 번째가 나와도 기록한다. "확인했고 없었다"는 "안 해봤다"와 완전히 다른 정보다.
나중에 마스코트에 애니메이션이 붙어 클릭 영역이 프레임마다 바뀌면 자연스럽게
`every-frame`에 가까워지므로, 지금 확인해 두면 그때 다시 걱정하지 않아도 된다.

### 3-3. 멀티모니터 / DPI

1. `F8`로 클릭 영역 외곽선 켜기
2. `F7`로 모니터를 옮겨가며, 외곽선 **안쪽**을 클릭하면 반응하고 **바깥**을 클릭하면 뒤 창이 눌리는지 확인
3. 배율이 다른 모니터(100% ↔ 125%/150%)에서 **외곽선과 실제 클릭 영역이 어긋나는지**가 핵심
4. HUD의 `dpi` / `scale` 값을 모니터별로 기록

> 어긋난다면 passthrough 좌표가 논리 픽셀이 아니라 물리 픽셀 기준이라는 뜻이다.
> `_win.ContentScaleFactor` 또는 `ScreenGetScale`로 보정해야 한다.

### 3-4. 전체화면 게임 위 동작

1. 보유한 게임을 **보더리스 풀스크린**으로 실행
2. 오버레이가 위에 보이는가 / 사라지는가
3. 게임 FPS가 떨어지는가
4. **배타적 풀스크린**으로 바꿔 다시 확인

> 배타적 풀스크린 위에 못 뜨는 건 정상이다. 버그가 아니라
> **"게임 실행 중엔 자동 숨김"이라는 기능 요구사항**으로 기획서에 반영한다.

### 3-5. 노트북 배터리

전원 뽑고 1시간 상주 → 설정 > 시스템 > 배터리 > 배터리 사용량에서 `ProjectSeWoo` 항목 확인.

### 메모리 초과 시 렌더러 A/B — 스크립트로 돌린다 (약 5분)

```powershell
powershell -ExecutionPolicy Bypass -File tools\measure-renderers.ps1
```

`project.godot`을 네 번 고치고 네 번 재시작할 필요 없다. Godot의
`--rendering-method` / `--rendering-driver` 오버라이드를 쓰므로 **프로젝트 파일이 전혀
바뀌지 않는다.** 측정 중에 작업 트리가 더러워지지 않고, 측정하다 만 설정이 커밋에
섞여 들어갈 일도 없다.

스크립트가 조건마다 하는 일: standalone 실행(디버거 없음) → 워밍 15초 → 45초 측정 →
리포트를 파일로 쓰고 자동 종료. 끝나면 §4에 그대로 붙일 수 있는 마크다운 표를 뱉는다.
`Win32_PerfFormattedData_PerfProc_Process`로 OS 카운터도 같이 찍어서 HUD의 `priv`와
교차 검증한다 — 두 값이 크게 다르면 `PerfProbe` 쪽을 의심해야 한다.

옵션: `-Seconds 60` (조건당 총 시간) / `-Warmup 15` / `-Godot <경로>` / `-OutDir <경로>`.

네 조건 모두 폴백 없이 요청한 렌더러로 초기화됐다(스크립트가 `실제 렌더러` 열로 확인).

**읽어낼 것 셋**

1. **`priv` 기준 150MB는 어떤 렌더러로도 못 맞춘다.** 최선인 `gl_compatibility`도 281MB로
   기준의 1.9배다. **렌더러 선택만으로는 이 게이트를 닫을 수 없다.** 남은 손잡이는
   `ExportRelease` 빌드뿐이고(§아래), 그래도 안 되면 기준 자체를 재검토해야 한다.
2. **Vulkan이 압도적으로 나쁘다.** `forward_plus`에서 드라이버만 d3d12 → vulkan으로 바꾸니
   335MB → 791MB로 2.4배가 됐다. CPU도 0.04% → 0.48%로 12배다. **Windows에서는 d3d12가
   기본값인 게 맞다**는 것이 우리 환경에서 확인됐다. `mobile/vulkan`이 `forward_plus/vulkan`보다
   나은 것도 렌더링 메서드가 아니라 드라이버가 지배적이라는 뜻이다.
3. **HUD `priv`와 OS `PrivCommit`이 일치한다** (335/336, 791/804, 649/635, 281/281).
   `PerfProbe`가 맞다는 것이 교차 검증됐다. 이제 HUD 숫자만 믿고 측정해도 된다.

**`gl_compatibility`에서 per-pixel 투명이 정상 동작했다 (9/14 육안 확인).**
이게 이번 스윕의 가장 큰 소득이다. 렌더링 경로가 통째로 다른 경로라 여기서 투명이
깨졌다면 메모리 최선 후보를 그냥 버려야 했다. 깨지지 않았으므로
**`gl_compatibility` / `opengl3`이 유효한 채택 후보로 남는다.**

#### `ExportRelease` 재측정 (2026-09-14, 같은 조건)

```powershell
powershell -ExecutionPolicy Bypass -File tools\measure-renderers.ps1 -Exe build\ProjectSeWoo.exe
```

| # | 렌더링 메서드 / 드라이버 | `priv` | `ws` | OS `PrivWS` | cpu avg | Debug 대비 `priv` |
|---|---|---|---|---|---|---|
| 1 | `forward_plus` / `d3d12` | 376MB | 374MB | 268MB | 0.19% | 335 → 376 (**+12%**) |
| 2 | `forward_plus` / `vulkan` | 641MB | 540MB | 372MB | 0.17% | 791 → 641 (-19%) |
| 3 | `mobile` / `vulkan` | 591MB | 504MB | 343MB | 0.03% | 649 → 591 (-9%) |
| 4 | `gl_compatibility` / `opengl3` | **228MB** | 207MB | **122MB** | **0.00%** | 281 → 228 (-19%) |

`gl_compatibility`는 Debug/Release 양쪽에서 per-pixel 투명이 정상이었다(육안 확인). 채택하지
않기로 했지만, **메모리를 깎아야 할 때 되돌아올 수 있는 검증된 선택지**로 남겨둔다.

**릴리스가 만능이 아니었다.** `d3d12`는 오히려 12% 늘었다(335 → 376MB). 릴리스 템플릿이
debug 템플릿보다 무조건 가볍다는 통념은 이 프로젝트에서 성립하지 않는다.
반대로 `gl_compatibility`는 19% 줄어 격차가 더 벌어졌다 — **릴리스에서 2위(`d3d12` 376MB)와
1.6배 차이다.** CPU도 `0.00%`로 측정 한계 아래다.

#### 결정 (2026-09-14) — 렌더러는 `forward_plus` / `d3d12` 유지

측정상 최선은 `gl_compatibility`였지만(`priv` 228MB / `PrivWS` 122MB, 2위와 1.6배 차),
**기존에 쓰던 `forward_plus` / `d3d12`를 그대로 간다.** `project.godot`은 이미 d3d12이므로
변경 없음.

이 결정으로 따라오는 것:

| | `d3d12` (채택) | `gl_compatibility` (미채택) |
|---|---|---|
| `priv` | 376MB | 228MB |
| `PrivWS` (유저가 보는 값) | **268MB** | 122MB |
| cpu avg | 0.19% | 0.00% |
| 플리커 재검증 | **불필요** — §3-2 Go 판정이 이 경로에서 나왔다 | 필요했을 것 |
| 투명 | 정상 (원래 경로) | 정상 (Debug/Release 모두 확인) |

**메모리 150MB 게이트는 `d3d12`에서 두 지표 모두 실패한다.** 보수적 지표(`priv` 376MB)는
물론이고, 관대한 지표(`PrivWS` 268MB)로 봐도 기준의 1.8배다. 즉 **렌더러를 d3d12로 두는 한
150MB는 지표를 바꿔서도 못 맞춘다.** 이 게이트는 열린 채로 남는다.

얻는 것도 있다 — **§3-2 플리커 Go 판정과 드래그·passthrough 관찰이 전부 이 경로에서
나온 결과라 그대로 유효하다.** 렌더러를 갈았다면 다시 봐야 했을 항목들이다.

**게이트 처리**: §7-3이 어차피 "커서 추종 창을 포함해서 실측"을 요구한다. 지금 셸 단독
숫자로 기준을 다시 쓰는 것보다, **A2에서 커서 창을 붙인 뒤 전체 숫자를 보고 한 번에
판정하는 것이 맞다.** 그때 선택지는 셋이다:

1. 기준 지표를 `PrivWS`로 바꾸고 상한을 현실에 맞게 재설정
2. 메모리를 실제로 깎는다 (`gl_compatibility` 재고 / .NET 트리밍 / GC 설정)
3. C#/.NET 자체를 재검토 (비용이 크다. 이미 일정이 밀린 상태에서는 마지막 수단)

> 이 숫자는 **셸 하나만**의 값이다. A2에서 창이 하나 더 붙으면 여기서 더 올라간다.

> **스크립트가 판정하지 못하는 게 하나 있다 — 투명.** 4번은 렌더링 경로가 통째로
> 바뀌므로 **per-pixel 투명이 그대로 되는지 반드시 눈으로 확인한다.** 메모리가 절반이
> 되어도 투명이 깨지면 쓸 수 없다. 깨지는 것 자체가 기록할 결과다. 그래서 스크립트는
> 창을 계속 띄워두고, 표의 `투명 정상?` 열은 비워서 내놓는다. **그 5분은 화면을 보고 있어라.**

> Godot은 요청한 렌더러를 못 쓰면 조용히 폴백한다. 스크립트가 `실제 렌더러` 열을 따로
> 뽑아 요청과 다르면 경고하는 이유다. 이걸 놓치면 전혀 다른 조건의 숫자를 비교하게 된다.

> 그래도 기준을 못 맞추면 `ExportRelease` 빌드로 재측정한다(지금은 `Debug` 빌드라 보수적).

```
export_presets.cfg         Windows Desktop 릴리스 익스포트 프리셋
build/                     익스포트 산출물 (gitignore)
```

릴리스 빌드는 헤드리스로 뽑는다 — W4의 A12(빌드 파이프라인)가 여기서 절반 끝났다:

```
Godot_..._console.exe --headless --path . --export-release "Windows Desktop" build\ProjectSeWoo.exe
```

**함정: 헤드리스 익스포트는 끝나고도 프로세스가 안 죽는다.** 패킹까지 `DONE`을 찍고
CPU 0%로 남아 있어서 강제 종료해야 했다. CI에 넣을 때 타임아웃 + kill 이 필요하다.

무인 측정 모드는 `OverlayShell.ParseAutoReportArgs()` / `TickAutoReport()`에 있다.
`-- --report=<경로> --seconds=<초> --warmup=<초>`를 넘기면 사람 없이 재고 종료한다.
`--` 뒤에 두는 이유는 Godot 자체 옵션과 섞이지 않게 하기 위해서다.

씬을 코드로 짓는 건 스파이크라서다. 에디터를 안 거쳐도 상태 전부가 한 파일에서 읽힌다.
게임 본편으로 넘어가면 씬은 에디터에서 짜야 한다.

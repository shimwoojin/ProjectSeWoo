### 밟은 함정 (다음에 또 밟지 말 것)

**1. Godot 표준 빌드는 C#을 못 읽는다**
`Godot_v4.7.2-stable_win64.exe`(표준)와 `Godot_v4.7.2-stable_mono_win64`(.NET)는 별도 다운로드다.
표준은 단일 exe, mono는 **폴더째**라 exe만 빼내면 실행되지 않는다.

**2. `Godot.Environment` vs `System.Environment` 이름 충돌**
`using Godot;` 상태에서 `Environment.ProcessorCount`를 쓰면 CS0104 모호성 에러.
`System.Environment`로 정규화해야 한다. `Godot.Environment`는 3D 월드 환경 리소스라 이름이 겹친다.

**3. Godot 기본 테마 폰트에 한글 글리프가 없다**
Label에 한글을 넣으면 두부(□)로 렌더된다. 그래서 HUD는 전부 영어로 썼다.
→ **게임 본편에서 한글 UI를 쓰려면 폰트를 번들해야 한다.** 라이선스 확인 필요(Pretendard / 나눔 계열).
Week 0 확인 항목에 추가.

**4. `per_pixel_transparency/allowed`는 런타임에 못 켠다**
`project.godot`에서 켜야 한다. 코드에서 켜려 하면 조용히 무시된다.

**5. 드래그 중에는 passthrough를 꺼야 한다**
클릭 영역(스프라이트 사각형) 밖으로 커서가 나가는 순간 마우스 이벤트가 끊겨 드래그가 풀린다.
`BeginDrag()`에서 빈 배열을 넘겨 창 전체가 마우스를 받게 하고, `EndDrag()`에서 복구한다.
추가로 창 밖으로 나가면 모션 이벤트 자체가 안 오므로, 위치 추적은 `_Process`에서 `DisplayServer.MouseGetPosition()` 폴링으로 한다.

### 구현 메모 — 플리커를 "실험"으로 만든 이유

[godot#80098](https://github.com/godotengine/godot/issues/80098): 투명창 + `window_set_mouse_passthrough` 조합에서 흰색 깜빡임 리포트.
이게 Day 1-2 최대 불확실성인데, 문서만 봐서는 "엔진이 못 하는 것"인지 "우리가 매 프레임 호출해서 그런 것"인지 알 수 없다.

그래서 `ApplyPassthrough(bool force)` 하나로 두 모드를 갖고, `F3`으로 즉시 전환하게 했다.

- `on-change` — 폴리곤이 실제로 바뀐 경우에만 `DisplayServer`를 건드린다 (회피 가설)
- `every-frame` — 매 프레임 강제 호출 (버그 재현)

`_regionWrites` 카운터로 두 모드의 실제 호출 횟수 차이가 HUD에 보인다.
**every-frame에서만 깜빡이면 회피책이 통하는 것이고, 곧 Go 판정이다.**

### 계측을 앱 안에 넣은 이유

합격 기준이 "유휴 CPU < 1%, 메모리 < 150MB"인데 작업관리자 곁눈질로는 기록이 안 남는다.
`PerfProbe`가 작업관리자와 같은 공식으로 계산한다:

```
CPU% = (프로세스 CPU 시간 델타) / (실제 경과 시간 × 논리 코어 수) × 100
```

`F9`를 누르면 노션 측정 기록표에 그대로 붙일 형태로 클립보드에 복사된다.

## 2026-09-13 — 개발 환경 / 워크플로 확정 (Visual Studio + Godot 에디터)

Godot 첫 프로젝트인데 팀의 배경이 언리얼이라, "어디까지가 에디터의 일이고 어디부터가
Visual Studio의 일인가"를 확정하지 않은 채로 작업하면 계속 헤맨다. 그래서 이번에 정리했다.

### 한 일

1. **VS에서 F5 디버깅이 되게 함** → `tools/VsLauncher` 런처 프로젝트 추가
2. **언어 방침 확정** — 우리 코드는 C# 단일. GDScript는 서드파티 애드온이 들고 올 때만 허용
3. `src/*.cs.uid` 커밋, `.gitignore`에 `.vs/`·`.idea/` 추가, 문서의 구 프로젝트명 경로 정리

### 언어: C# 단일로 간다

Godot은 노드 하나에 스크립트 하나를 붙이는 구조라 C#과 GDScript를 같은 트리에 섞을 수 있다.
하지만 경계를 넘는 호출이 `node.Call("method_name", args)` 형태의 **문자열 기반 동적 디스패치**다.
메서드명 오타, 인자 개수 실수, 이름 변경 리팩터링이 전부 런타임에야 터진다.
2인 / 1개월에서 낼 비용이 아니다.

| 대상 | 언어 |
|---|---|
| 우리가 쓰는 게임·셸 코드 | **C#** |
| 서드파티 애드온이 GDScript로 와 있는 경우 (`addons/`) | 그대로 쓰고 얇은 C# 래퍼로 격리 |
| 튜토리얼·문서·StackOverflow | 전부 GDScript. **읽고 번역하는 비용은 계속 든다** |

마지막 줄은 WEEK0 §9가 지적한 A안의 실질 리스크 그대로다. 다만 이것은 *섞어 쓰는* 비용이
아니라 *읽는* 비용이므로, GDScript를 프로젝트에 들이는 것으로 해결되지 않는다.
대응은 "GDScript를 읽을 수 있을 정도로만 익히기"뿐이다.

### 언리얼 ↔ Godot 대응

| 언리얼 | Godot |
|---|---|
| `.uproject` | `project.godot` (파일) |
| `Intermediate/`, `DerivedDataCache/` | `.godot/` (폴더, 순수 캐시) |
| `Content/` + `.uasset` | 프로젝트 폴더 전체. Content/Source 구분 없음 |

| Epic Launcher Library | Project Manager (exe를 인자 없이 실행) |

### PIE에 대응하는 것은 없다. 둘로 쪼개져 있다

언리얼 PIE는 게임이 에디터 프로세스 *안에서* 돌기 때문에 디버거 하나로 전부 본다.
**Godot은 게임이 항상 별도 프로세스다.** 에디터에서 F5를 눌러도 게임은 자식 프로세스로 뜬다.
그래서 PIE가 한 번에 주던 두 가지가 서로 다른 도구로 갈린다.

| PIE가 주던 것 | Godot에서는 |
|---|---|
| C# 중단점 / 스텝 / 로컬 변수 | **Visual Studio** |
| 실행 중 씬 트리 보기, 노드 프로퍼티 실시간 수정 | **Godot 에디터 `디버거` 패널 → `Remote` 탭** |

| 실행 방법 | C# 중단점 | Remote 씬 트리 |
|---|---|---|
| VS에서 F5 (`VsLauncher`) | O — `_Ready()` 등 기동 코드도 잡힌다 | X (에디터가 띄운 게 아니라 연결되지 않음) |
| Godot 에디터에서 F5 | `Ctrl+Alt+P` 연결 시 O (기동 코드는 놓친다) | O |

"로직 버그 추적"이냐 "눈으로 확인·튜닝"이냐로 띄우는 쪽을 고른다. 둘 다 필요한 경우는 드물다.
(미검증 아이디어: 에디터 `디버그 > 디버그 서버 계속 열어두기` + 게임에
`--remote-debug tcp://127.0.0.1:6007` 인자를 주면 양쪽을 동시에 얻을 수 있을 가능성이 있다)

### 확정된 작업 루프

```
[코드]  VS 열고 수정 → Ctrl+Shift+B (에러를 VS 에러 목록에서 먼저 잡기) → F5
        시작 프로젝트는 VsLauncher 로 고정해 둔다. 왕복할 필요 없다.

[씬/에셋/프로젝트 설정]  project.godot 더블클릭 또는 Project Manager → Godot 에디터

[동시] 에디터로 씬 짜면서 VS로 F5 디버깅 가능. 프로세스가 달라 공존한다.
       드물게 어셈블리 파일 락이 나면 한쪽에서만 빌드한다.
```

**빌드가 언제 필요한가** — 에디터를 열기 전에 미리 빌드해 둘 필요는 없다.
에디터는 필요하면 스스로 빌드하고, 에디터에서 F5를 눌러도 stale하면 빌드한다.
명시적 빌드(에디터 우상단 망치 버튼)가 필요한 경우는 하나뿐이다:
**새 C# 클래스나 `[Export]` / `[Signal]`을 추가해서 그것이 에디터 UI(노드 추가 목록, 인스펙터)에
나타나게 하고 싶을 때.** 에디터는 소스를 파싱하지 않고 컴파일된 어셈블리에서 타입 정보를 읽는다.

빌드 출력은 `bin/`이 아니라 **`.godot\mono\temp\bin\Debug\ProjectSeWoo.dll`** 이다.
`Godot.NET.Sdk`가 경로를 리다이렉트한다. `.gitignore`의 `.godot/` 한 줄에 이미 걸린다.

### `tools/VsLauncher` — VS에서 F5가 안 되는 문제의 해결

`ProjectSeWoo`는 **클래스 라이브러리**다. 우리가 게임 exe를 빌드하는 것이 아니라
**Godot exe가 호스트이고 `ProjectSeWoo.dll`을 로드**하는 구조이기 때문이다.
VS는 시작 프로젝트가 될 수 있는지를 출력 형식으로 먼저 판단하고, Library면
실행 프로필을 아예 읽지 않는다. `.csproj.user`에 넣어도, 속성 UI로 넣어도 무시된다.
(Visual Studio 기준. VS Code + Godot Tools 나 Rider는 이 시나리오를 정식 지원한다)

그래서 **시작 가능한 Exe 프로젝트를 통행증으로 하나 두고 실행 대상만 바꿔치기한다.**

```
F5
 → ① VsLauncher 는 OutputType=Exe → "시작 가능" 판정 통과
 → ② 솔루션 빌드 (ProjectSeWoo.dll + pdb 갱신)
 → ③ launchSettings.json 의 commandName="Executable" 프로필이
      VsLauncher.exe 대신 Godot exe 를 디버거 아래에서 실행
      (VsLauncher 의 코드는 한 줄도 실행되지 않는다)
 → ④ Godot 이 게임으로 부팅 → ProjectSeWoo.dll 로드
 → ⑤ VS 가 어셈블리 로드를 감지해 옆의 pdb 로 중단점 바인딩
```

`tools/VsLauncher/Properties/launchSettings.json`의 프로필 이름이 VS 툴바 드롭다운에
그대로 나오므로, 이름에 판단 근거를 박아 두었다:

| 프로필 | 인자 | 용도 |
|---|---|---|
| `Godot 게임 (중단점 O)` | `--path .` | 평소 디버깅 |
| `Godot 에디터 (중단점 X)` | `--path . -e` | VS에서 에디터를 열 때 |

팀원 셋업은 `launchSettings.json`의 `executablePath` **한 줄**을 자기 엔진 경로로 고치는 것뿐이다.

### 밟은 함정 (이어서. 1~5는 2026-09-01 항목)

**6. VS는 출력 형식이 클래스 라이브러리인 프로젝트를 시작할 수 없다**
위 `tools/VsLauncher` 항목 참고. `.csproj.user`나 속성 UI로는 우회 불가.

**7. 에디터 플래그 `-e`를 주면 중단점이 절대 걸리지 않는다**
`-e`를 주면 에디터가 뜨고, 에디터의 F5는 게임을 *자식 프로세스*로 띄운다.
디버거는 에디터에 붙어 있으므로 게임 코드 중단점이 걸릴 수 없다.
`-e` 없이 `--path`만 주면 게임이 그 프로세스에서 직접 돌아 중단점이 걸린다.

**8. `project.godot`에 주석을 쓰지 마라**
Godot 에디터가 이 파일을 재저장할 때 **주석을 보존하지 않는다.** 실제로 2026-09-01에
넣어둔 주석이 전부 날아갔다. 또 기본값과 같은 항목은 생략하므로
`window/stretch/mode="disabled"`도 사라졌다(기본값이므로 동작은 동일).
→ 설계 근거 메모는 `docs/`나 C# 코드 주석에 둔다.

**9. `Godot.NET.Sdk`는 프로젝트 폴더 하위의 모든 `.cs`를 컴파일한다**
`tools/`를 그냥 만들면 런처 코드가 `ProjectSeWoo.dll` 안에 들어간다.
`<Compile Remove="tools/**" />`로 MSBuild 쪽을, `tools/.gdignore`로 Godot 에디터 쪽을 막았다.

**10. VS의 시작 프로젝트는 `.sln`이 아니라 `.suo`에 저장된다**
`.sln`을 손으로 고쳐 프로젝트를 추가해도 시작 프로젝트는 바뀌지 않는다.
`.vs\ProjectSeWoo\v18\.suo`에 들어 있고 VS UI에서만 바꾼다
(`VsLauncher` 우클릭 → `시작 프로젝트로 설정`, 설정되면 이름이 굵게 표시된다).

### 메모리를 판정하지 못한 이유 — 계측 지표를 잘못 골랐다

첫 측정에서 `329MB`가 나왔는데 내역이 맞지 않았다: `godot 81MB + clr heap 2MB = 83MB`인데
전체가 329MB. 원인은 `PerfProbe`가 `Process.WorkingSet64`를 쓰고 있었던 것이다.
이 값은 **공유 페이지를 포함한 전체 작업 집합**이고, D3D12 런타임 / GPU 드라이버 /
.NET 런타임의 DLL 페이지가 모두 들어간다. 우리 앱의 점유를 과대평가한다.

세 지표를 구분해야 한다. 대체로 `개인 작업 집합` <= `개인 커밋` <= `전체 작업 집합`이다.

| 지표 | 성격 | 어디서 |
|---|---|---|
| 전체 작업 집합 | 공유 DLL 페이지 포함 → 과대평가 | HUD `ws` |
| 개인 커밋 | 이 프로세스만 책임지는 커밋. **판정 기준** | HUD `priv`, 작업관리자 `커밋 크기` |
| 개인 작업 집합 | 물리 RAM 중 우리만 쓰는 부분. **유저가 보는 값** | 작업관리자 `메모리`(기본 열) |

`PrivateCommitMb`를 추가하고 주석을 고쳤다. 정식 재측정은 다음 세션.

**참고값** (판정 근거 아님) — 세션 도중 `Win32_PerfFormattedData_PerfProc_Process`로 관측한
Godot 프로세스: `PrivWS 236MB` / `WS 355MB` / `PrivCommit 351MB`.
측정 시점의 HUD 설정을 확인하지 않았고 관측 프로세스가 게임인지 에디터인지도 확정하지 않았다.

### A8 설계에서 실제로 고민한 것 — "스팀 없이도 앱은 온전하다"

보통 스팀 게임은 스팀이 없으면 안 켜진다. **우리는 그러면 안 된다.** 상주
오버레이라 스팀을 안 켠 채 켜져 있는 시간이 더 길고, A6 자동 시작을 켜면 로그인
직후 — 스팀이 뜨기 한참 전에 — 우리가 먼저 뜬다.

그래서 초기화 실패를 **오류가 아니라 상태**로 만들었다. 여기서 두 가지가 따라 나왔다.

1. **30초 재시도.** 한 번 실패하고 끝내면 그 세션 내내 멀티·도전과제가 죽는다.
   유저가 나중에 스팀을 켜도 소용없다. 부팅 자동 시작이면 첫 시도는 거의 항상 실패한다
2. **`RestartAppIfNecessary`를 쓰지 않는다.** 스팀 게임의 표준 관행이지만, 부팅
   자동 시작 앱이 이걸 부르면 **유저가 요청한 적 없는 스팀을 강제로 띄우고 자기를
   재실행한다.** 최악의 경우 부팅 때마다 반복된다. 빌드 제출(A12) 때 한 번 더 확인한다

`--steam` 스위치를 그 목적으로 넣었다(기본은 꺼짐 — 아래 함정 20).

| 조건 (커서 포함, Debug) | 개인 커밋 | 작업 집합 | 유휴 CPU |
|---|---|---|---|
| 스팀 없음 | 355 MB | 354 MB | 0.20% |
| **스팀 있음** | **379 MB** | 380 MB | 0.15% |
| 차이 | **+24 MB** | +26 MB | 오차 범위 |

연결 자체는 `--steam-selftest`(헤드리스, 종료 코드 0/1)로 확인했다 — 실제 계정

나중에 진짜 앱 ID로 이 검사를 돌렸을 때 실제 도전과제가 해금돼 버린다.

Godot에 3D 환경 리소스 `Environment`가 있어서 `Environment.SetEnvironmentVariable`이
컴파일 오류가 난다. `System.Environment`로 명시해야 한다. **`platform/` 파일이 전부
`using Godot;`을 달고 있으므로 `System.*`의 흔한 이름을 쓸 때마다 재발한다.**

**18. `Callback<T>` 핸들을 필드로 안 붙들면 콜백이 조용히 죽는다**
`Callback<UserStatsReceived_t>.Create(...)`의 반환값을 버리면 GC가 걷어가고, 그때부터
`RunCallbacks()`가 아무것도 부르지 않는다. **예외도 로그도 없다 — 그냥 영원히 안 온다.**
A9~A11에서 로비/P2P 콜백을 붙일 때 같은 함정이 그대로 반복된다.

**19. NuGet에 네이티브가 없고, `lib/`에 있는 건 참조 어셈블리다**
`Steamworks.NET` NuGet에는 관리 어셈블리만 들어 있다 — `steam_api64.dll`은 GitHub
릴리스에서 **같은 태그**로 따로 받아야 한다(버전이 어긋나면 `Packsize.Test()`에서
갈린다). 게다가 `lib/netstandard2.1/`의 것은 실행용이 아닌 **참조 어셈블리**이고
실제 구현은 `runtimes/<rid>/`에만 있다. Godot의 로드 컨텍스트가 `.deps.json`의
`runtimeTargets`를 읽어서 정상 해석됐지만, **운이 좋은 게 아니라 확인해야 아는
것이었다.** 엔진 버전이 올라가면 다시 봐야 한다.

**20. 무인 측정에서 스팀이 켜지면 안 된다**
`--report=` 측정이 스팀을 켜면 친구 목록에 "게임 중"이 뜨고 그 자체가 측정에 잡히는
부하다. `measure-renderers.ps1`은 조건마다 재시작하므로 네 번 깜빡인다. A6 트레이
아이콘이 이미 같은 이유로 `_unattended`에 묶여 있었고, 스팀도 같은 플래그에 묶었다.
**프로세스 밖으로 새어나가는 부작용은 전부 이 플래그 하나로 모은다**는 규칙이
세 번째로 값을 했다(세이브 파일 → 레지스트리 → 스팀).

나머지 A8 함정(`steam_appid.txt`의 작업 디렉터리 의존 등)은 [A8-STEAM.md](A8-STEAM.md) §5.

### 밟은 함정 (다음에 또 밟지 말 것)

**1. Godot 표준 빌드는 C#을 못 읽는다**
`Godot_v4.7.2-stable_win64.exe`(표준)와 `Godot_v4.7.2-stable_mono_win64`(.NET)는 별도 다운로드다.
표준은 단일 exe, mono는 **폴더째**라 exe만 빼내면 실행되지 않는다.

**2. `Godot.Environment` vs `System.Environment` 이름 충돌**
`using Godot;` 상태에서 `Environment.ProcessorCount`를 쓰면 CS0104 모호성 에러.
`System.Environment`로 정규화해야 한다. `Godot.Environment`는 3D 월드 환경 리소스라 이름이 겹친다.

**3. ~~Godot 기본 테마 폰트에 한글 글리프가 없다~~ — 오진이었다 (2026-09-16 정정)**
당시 Label 한글이 두부(□)로 나온 것을 보고 "기본 폰트에 글리프가 없다"고 적었고,
그래서 HUD를 전부 영어로 썼다. **그런데 A6 옵션 창은 폰트를 번들하지 않고도 한글이
정상으로 나온다** — 리포지토리에 `.ttf`/`.otf` 가 하나도 없고 `AddThemeFontOverride`
도 안 쓰는데 "설정 / 크기 / 투명도 / 위치 잠금 / 커서 장식" 이 전부 제대로 렌더된다.
→ 한글 UI 에 폰트 번들이 **필수는 아니다.** 원인은 따로 있었을 것이다(당시 씬/테마
구성으로 추정). 디자인상 원하는 서체를 쓰려면 번들하면 되고, 그때 라이선스를
확인하면 된다(Pretendard / 나눔 계열). **"안 나온다"를 전제로 계획을 잡지 말 것.**

**4. `per_pixel_transparency/allowed`는 런타임에 못 켠다**
`project.godot`에서 켜야 한다. 코드에서 켜려 하면 조용히 무시된다.

**5. 드래그 중에는 passthrough를 꺼야 한다**
클릭 영역(스프라이트 사각형) 밖으로 커서가 나가는 순간 마우스 이벤트가 끊겨 드래그가 풀린다.
`BeginDrag()`에서 빈 배열을 넘겨 창 전체가 마우스를 받게 하고, `EndDrag()`에서 복구한다.
추가로 창 밖으로 나가면 모션 이벤트 자체가 안 오므로, 위치 추적은 `_Process`에서 `DisplayServer.MouseGetPosition()` 폴링으로 한다.

### 구현 메모 — 플리커를 "실험"으로 만든 이유

[godot#80098](https://github.com/godotengine/godot/issues/80098): 투명창 + `window_set_mouse_passthrough` 조합에서 흰색 깜빡임 리포트.
이게 Day 1-2 최대 불확실성인데, 문서만 봐서는 "엔진이 못 하는 것"인지 "우리가 매 프레임 호출해서 그런 것"인지 알 수 없다.

그래서 `ApplyPassthrough(bool force)` 하나로 두 모드를 갖고, `F3`으로 즉시 전환하게 했다.

- `on-change` — 폴리곤이 실제로 바뀐 경우에만 `DisplayServer`를 건드린다 (회피 가설)
- `every-frame` — 매 프레임 강제 호출 (버그 재현)

`_regionWrites` 카운터로 두 모드의 실제 호출 횟수 차이가 HUD에 보인다.
**every-frame에서만 깜빡이면 회피책이 통하는 것이고, 곧 Go 판정이다.**

### 계측을 앱 안에 넣은 이유

합격 기준이 "유휴 CPU < 1%, 메모리 < 150MB"인데 작업관리자 곁눈질로는 기록이 안 남는다.
`PerfProbe`가 작업관리자와 같은 공식으로 계산한다:

```
CPU% = (프로세스 CPU 시간 델타) / (실제 경과 시간 × 논리 코어 수) × 100
```

`F9`를 누르면 노션 측정 기록표에 그대로 붙일 형태로 클립보드에 복사된다.

Godot 첫 프로젝트인데 팀의 배경이 언리얼이라, "어디까지가 에디터의 일이고 어디부터가
Visual Studio의 일인가"를 확정하지 않은 채로 작업하면 계속 헤맨다. 그래서 이번에 정리했다.

### 한 일

2. **언어 방침 확정** — 우리 코드는 C# 단일. GDScript는 서드파티 애드온이 들고 올 때만 허용
3. `src/*.cs.uid` 커밋, `.gitignore`에 `.vs/`·`.idea/` 추가, 문서의 구 프로젝트명 경로 정리

### 언어: C# 단일로 간다

Godot은 노드 하나에 스크립트 하나를 붙이는 구조라 C#과 GDScript를 같은 트리에 섞을 수 있다.
하지만 경계를 넘는 호출이 `node.Call("method_name", args)` 형태의 **문자열 기반 동적 디스패치**다.
메서드명 오타, 인자 개수 실수, 이름 변경 리팩터링이 전부 런타임에야 터진다.
2인 / 1개월에서 낼 비용이 아니다.

| 대상 | 언어 |
|---|---|
| 우리가 쓰는 게임·셸 코드 | **C#** |
| 서드파티 애드온이 GDScript로 와 있는 경우 (`addons/`) | 그대로 쓰고 얇은 C# 래퍼로 격리 |
| 튜토리얼·문서·StackOverflow | 전부 GDScript. **읽고 번역하는 비용은 계속 든다** |

마지막 줄은 WEEK0 §9가 지적한 A안의 실질 리스크 그대로다. 다만 이것은 *섞어 쓰는* 비용이
아니라 *읽는* 비용이므로, GDScript를 프로젝트에 들이는 것으로 해결되지 않는다.
대응은 "GDScript를 읽을 수 있을 정도로만 익히기"뿐이다.

### 언리얼 ↔ Godot 대응

| 언리얼 | Godot |
|---|---|
| `.uproject` | `project.godot` (파일) |
| `Intermediate/`, `DerivedDataCache/` | `.godot/` (폴더, 순수 캐시) |
| `Content/` + `.uasset` | 프로젝트 폴더 전체. Content/Source 구분 없음 |

| Epic Launcher Library | Project Manager (exe를 인자 없이 실행) |

### PIE에 대응하는 것은 없다. 둘로 쪼개져 있다

언리얼 PIE는 게임이 에디터 프로세스 *안에서* 돌기 때문에 디버거 하나로 전부 본다.
**Godot은 게임이 항상 별도 프로세스다.** 에디터에서 F5를 눌러도 게임은 자식 프로세스로 뜬다.
그래서 PIE가 한 번에 주던 두 가지가 서로 다른 도구로 갈린다.

| PIE가 주던 것 | Godot에서는 |
|---|---|
| C# 중단점 / 스텝 / 로컬 변수 | **Visual Studio** |
| 실행 중 씬 트리 보기, 노드 프로퍼티 실시간 수정 | **Godot 에디터 `디버거` 패널 → `Remote` 탭** |

| 실행 방법 | C# 중단점 | Remote 씬 트리 |
|---|---|---|
| VS에서 F5 (`VsLauncher`) | O — `_Ready()` 등 기동 코드도 잡힌다 | X (에디터가 띄운 게 아니라 연결되지 않음) |
| Godot 에디터에서 F5 | `Ctrl+Alt+P` 연결 시 O (기동 코드는 놓친다) | O |

"로직 버그 추적"이냐 "눈으로 확인·튜닝"이냐로 띄우는 쪽을 고른다. 둘 다 필요한 경우는 드물다.
(미검증 아이디어: 에디터 `디버그 > 디버그 서버 계속 열어두기` + 게임에
`--remote-debug tcp://127.0.0.1:6007` 인자를 주면 양쪽을 동시에 얻을 수 있을 가능성이 있다)

### 확정된 작업 루프

```
[코드]  VS 열고 수정 → Ctrl+Shift+B (에러를 VS 에러 목록에서 먼저 잡기) → F5
        시작 프로젝트는 VsLauncher 로 고정해 둔다. 왕복할 필요 없다.

[씬/에셋/프로젝트 설정]  project.godot 더블클릭 또는 Project Manager → Godot 에디터

[동시] 에디터로 씬 짜면서 VS로 F5 디버깅 가능. 프로세스가 달라 공존한다.
       드물게 어셈블리 파일 락이 나면 한쪽에서만 빌드한다.
```

**빌드가 언제 필요한가** — 에디터를 열기 전에 미리 빌드해 둘 필요는 없다.
에디터는 필요하면 스스로 빌드하고, 에디터에서 F5를 눌러도 stale하면 빌드한다.
명시적 빌드(에디터 우상단 망치 버튼)가 필요한 경우는 하나뿐이다:
**새 C# 클래스나 `[Export]` / `[Signal]`을 추가해서 그것이 에디터 UI(노드 추가 목록, 인스펙터)에
나타나게 하고 싶을 때.** 에디터는 소스를 파싱하지 않고 컴파일된 어셈블리에서 타입 정보를 읽는다.

빌드 출력은 `bin/`이 아니라 **`.godot\mono\temp\bin\Debug\ProjectSeWoo.dll`** 이다.
`Godot.NET.Sdk`가 경로를 리다이렉트한다. `.gitignore`의 `.godot/` 한 줄에 이미 걸린다.

### `tools/VsLauncher` — VS에서 F5가 안 되는 문제의 해결

`ProjectSeWoo`는 **클래스 라이브러리**다. 우리가 게임 exe를 빌드하는 것이 아니라
**Godot exe가 호스트이고 `ProjectSeWoo.dll`을 로드**하는 구조이기 때문이다.
VS는 시작 프로젝트가 될 수 있는지를 출력 형식으로 먼저 판단하고, Library면
실행 프로필을 아예 읽지 않는다. `.csproj.user`에 넣어도, 속성 UI로 넣어도 무시된다.
(Visual Studio 기준. VS Code + Godot Tools 나 Rider는 이 시나리오를 정식 지원한다)

그래서 **시작 가능한 Exe 프로젝트를 통행증으로 하나 두고 실행 대상만 바꿔치기한다.**

```
F5
 → ① VsLauncher 는 OutputType=Exe → "시작 가능" 판정 통과
 → ② 솔루션 빌드 (ProjectSeWoo.dll + pdb 갱신)
 → ③ launchSettings.json 의 commandName="Executable" 프로필이
      VsLauncher.exe 대신 Godot exe 를 디버거 아래에서 실행
      (VsLauncher 의 코드는 한 줄도 실행되지 않는다)
 → ④ Godot 이 게임으로 부팅 → ProjectSeWoo.dll 로드
 → ⑤ VS 가 어셈블리 로드를 감지해 옆의 pdb 로 중단점 바인딩
```

`tools/VsLauncher/Properties/launchSettings.json`의 프로필 이름이 VS 툴바 드롭다운에
그대로 나오므로, 이름에 판단 근거를 박아 두었다:

| 프로필 | 인자 | 용도 |
|---|---|---|
| `Godot 게임 (중단점 O)` | `--path .` | 평소 디버깅 |
| `Godot 에디터 (중단점 X)` | `--path . -e` | VS에서 에디터를 열 때 |

팀원 셋업은 `launchSettings.json`의 `executablePath` **한 줄**을 자기 엔진 경로로 고치는 것뿐이다.

### 밟은 함정 (이어서. 1~5는 2026-09-01 항목)

**6. VS는 출력 형식이 클래스 라이브러리인 프로젝트를 시작할 수 없다**
위 `tools/VsLauncher` 항목 참고. `.csproj.user`나 속성 UI로는 우회 불가.

**7. 에디터 플래그 `-e`를 주면 중단점이 절대 걸리지 않는다**
`-e`를 주면 에디터가 뜨고, 에디터의 F5는 게임을 *자식 프로세스*로 띄운다.
디버거는 에디터에 붙어 있으므로 게임 코드 중단점이 걸릴 수 없다.
`-e` 없이 `--path`만 주면 게임이 그 프로세스에서 직접 돌아 중단점이 걸린다.

**8. `project.godot`에 주석을 쓰지 마라**
Godot 에디터가 이 파일을 재저장할 때 **주석을 보존하지 않는다.** 실제로 2026-09-01에
넣어둔 주석이 전부 날아갔다. 또 기본값과 같은 항목은 생략하므로
`window/stretch/mode="disabled"`도 사라졌다(기본값이므로 동작은 동일).
→ 설계 근거 메모는 `docs/`나 C# 코드 주석에 둔다.

**9. `Godot.NET.Sdk`는 프로젝트 폴더 하위의 모든 `.cs`를 컴파일한다**
`tools/`를 그냥 만들면 런처 코드가 `ProjectSeWoo.dll` 안에 들어간다.
`<Compile Remove="tools/**" />`로 MSBuild 쪽을, `tools/.gdignore`로 Godot 에디터 쪽을 막았다.

**10. VS의 시작 프로젝트는 `.sln`이 아니라 `.suo`에 저장된다**
`.sln`을 손으로 고쳐 프로젝트를 추가해도 시작 프로젝트는 바뀌지 않는다.
`.vs\ProjectSeWoo\v18\.suo`에 들어 있고 VS UI에서만 바꾼다
(`VsLauncher` 우클릭 → `시작 프로젝트로 설정`, 설정되면 이름이 굵게 표시된다).
증상: 빌드는 성공한 뒤에 "시작할 수 없습니다" 문구가 뜬다.
또 솔루션이 열린 상태에서 `.sln`을 외부에서 고쳤다면 솔루션을 닫고 다시 열어야 반영된다.

**11. `.cs.uid` / `.import`는 커밋 대상이다**
Godot 4.4+는 스크립트에도 `uid://`를 부여하고 `파일명.cs.uid`로 저장한다. 파일을 옮기거나

### 메모리를 판정하지 못한 이유 — 계측 지표를 잘못 골랐다

첫 측정에서 `329MB`가 나왔는데 내역이 맞지 않았다: `godot 81MB + clr heap 2MB = 83MB`인데
전체가 329MB. 원인은 `PerfProbe`가 `Process.WorkingSet64`를 쓰고 있었던 것이다.
이 값은 **공유 페이지를 포함한 전체 작업 집합**이고, D3D12 런타임 / GPU 드라이버 /
.NET 런타임의 DLL 페이지가 모두 들어간다. 우리 앱의 점유를 과대평가한다.

세 지표를 구분해야 한다. 대체로 `개인 작업 집합` <= `개인 커밋` <= `전체 작업 집합`이다.

| 지표 | 성격 | 어디서 |
|---|---|---|
| 전체 작업 집합 | 공유 DLL 페이지 포함 → 과대평가 | HUD `ws` |
| 개인 커밋 | 이 프로세스만 책임지는 커밋. **판정 기준** | HUD `priv`, 작업관리자 `커밋 크기` |
| 개인 작업 집합 | 물리 RAM 중 우리만 쓰는 부분. **유저가 보는 값** | 작업관리자 `메모리`(기본 열) |

`PrivateCommitMb`를 추가하고 주석을 고쳤다. 정식 재측정은 다음 세션.

**참고값** (판정 근거 아님) — 세션 도중 `Win32_PerfFormattedData_PerfProc_Process`로 관측한
Godot 프로세스: `PrivWS 236MB` / `WS 355MB` / `PrivCommit 351MB`.
측정 시점의 HUD 설정을 확인하지 않았고 관측 프로세스가 게임인지 에디터인지도 확정하지 않았다.

### A8 설계에서 실제로 고민한 것 — "스팀 없이도 앱은 온전하다"

보통 스팀 게임은 스팀이 없으면 안 켜진다. **우리는 그러면 안 된다.** 상주
오버레이라 스팀을 안 켠 채 켜져 있는 시간이 더 길고, A6 자동 시작을 켜면 로그인
직후 — 스팀이 뜨기 한참 전에 — 우리가 먼저 뜬다.

그래서 초기화 실패를 **오류가 아니라 상태**로 만들었다. 여기서 두 가지가 따라 나왔다.

1. **30초 재시도.** 한 번 실패하고 끝내면 그 세션 내내 멀티·도전과제가 죽는다.
   유저가 나중에 스팀을 켜도 소용없다. 부팅 자동 시작이면 첫 시도는 거의 항상 실패한다
2. **`RestartAppIfNecessary`를 쓰지 않는다.** 스팀 게임의 표준 관행이지만, 부팅
   자동 시작 앱이 이걸 부르면 **유저가 요청한 적 없는 스팀을 강제로 띄우고 자기를
   재실행한다.** 최악의 경우 부팅 때마다 반복된다. 빌드 제출(A12) 때 한 번 더 확인한다

### A8 실측 — 스팀은 개인 커밋 +24MB, CPU는 영향 없음

A7 메모리 게이트가 **조건부 Go**인 상태에서 새 네이티브 런타임을 얹는 작업이라,
안 재고 넘어가면 나중에 원인을 못 찾는다. 무인 측정에서 스팀을 일부러 켜는
`--steam` 스위치를 그 목적으로 넣었다(기본은 꺼짐 — 아래 함정 20).

| 조건 (커서 포함, Debug) | 개인 커밋 | 작업 집합 | 유휴 CPU |
|---|---|---|---|
| 스팀 없음 | 355 MB | 354 MB | 0.20% |
| **스팀 있음** | **379 MB** | 380 MB | 0.15% |
| 차이 | **+24 MB** | +26 MB | 오차 범위 |

**CPU는 영향이 없다.** 콜백 펌프를 매 프레임 돌리는데도 §7-3의 1% 기준 안이다.
**메모리는 여유가 줄었다** — 기준(`PrivWS < 300MB`) 안이긴 하나, A7이 추정 근거로

## 2026-09-16 (이어서) — A7 Release 실측: `PrivWS` 239MB, **확정 Go**

### 막혀 있던 게 이미 안 막혀 있었다

A7 §3은 "export 템플릿이 이 PC에 없다"로 끝나 있었고, 나는 몇백MB~1GB 다운로드를
각오하고 들어갔다. **이미 설치돼 있었다** (`%APPDATA%\Godot\export_templates\
4.7.2.stable.mono\`, 27개 파일, `windows_release_x86_64.exe` 포함). `version.txt`가
`4.7.2.stable.mono`로 엔진과 일치하는 것까지 확인하고 바로 익스포트로 넘어갔다.

**문서에 "못 했다"고 적힌 항목은 착수 전에 현재 상태부터 확인해야 한다.** 세션이
끊긴 사이에 해결돼 있을 수 있고, 여기서는 그게 30분짜리 다운로드였다.

### 판정 — 확정 Go. 그리고 스팀 비용의 해석이 바뀌었다

| 조건 | `priv`(커밋) | **OS `PrivWS`** | cpu avg |
|---|---|---|---|
| 스팀 off (2회) | 343 | **235** | 0.22% |
| **스팀 on (3회)** | 367 | **239** | 0.14% |

기준 `PrivWS` < 300MB 대비 **61MB(20%) 여유**. §4가 비율 0.71로 추정한 276MB보다
**37MB 가벼웠다** — 실제 비율은 0.65다. 추정이 안전한 쪽으로 틀렸다.

**여기서 A8의 결론 하나를 다시 읽어야 한다.** A8은 "스팀이 +24MB, 메모리 여유가
줄었다"고 썼다. 커밋 기준 +24MB는 **Release에서도 정확히 재현됐다**(343→367).
그런데 **정식 기준인 `PrivWS`로는 +4MB뿐이다**(235→239). 스팀 런타임은 커밋을 크게
예약하지만 실제로 상주시키는 페이지는 훨씬 적다. **A8이 틀린 게 아니라, 09-16에
기준 지표를 바꾼 뒤로 같은 사실의 의미가 달라진 것이다.** 지표를 바꿀 때는 그
지표로 내렸던 과거 판정을 다시 읽어야 한다는 게 교훈이다.

부수적으로 **`gl_compatibility` 재도전 카드는 철회했다.** 20% 여유가 실측으로
확인된 이상, 플리커 재검증(§3-2)이라는 비싼 값을 치를 이유가 없다.

### `--steam-selftest`가 무인 플래그를 빠져나가고 있었다

익스포트 바이너리에서 스팀이 붙는지 확인하려고 `--steam-selftest`를 **창 있는 채로**
돌렸다. A8은 이걸 항상 헤드리스로만 돌렸다. 그랬더니:

```
[autostart] 해제
[tray] indicator id=0
[steam] 연결됨 appid=480 user=... (Spacewar 임시 ID)
```

**트레이 아이콘이 떴고, 레지스트리 Run 키를 건드렸고, 세이브 파일을 덮었다.**
`IsUnattendedRun()`이 `--selftest`(정확히 일치)와 `--report=`(접두사)만 보는데
`--steam-selftest`는 **둘 다 아니다.** 헤드리스면 `DisplayServer.GetName()`으로
걸리니까 A8에서는 안 드러났을 뿐이다.

이 함수의 주석에는 **"프로세스 밖으로 새어나가는 부작용을 전부 막는다"**고 적혀
있고, A3에서 세이브 파일을 덮은 사고 때문에 만든 플래그다. **그 플래그를 인자
이름으로 하나씩 열거하는 방식이 다음 인자에서 바로 샜다.** 접미사 매칭으로 고쳤다 —
`--net-selftest` 같은 게 A9~A11에서 늘어도 같은 실수가 안 난다.

피해는 없었다. Run 키에 우리 항목이 애초에 없었고(`autostart: false`),
`[autostart] 해제`는 없는 것을 다시 없앤 no-op였다. **세이브 파일은 실제로
덮였지만**(창 위치만) 개발용 값이었다.

### 헬퍼를 어떻게 뽑을지가 A12 의 실제 내용이었다

**AOT 로 갔다.** 70MB 를 아끼는 것보다, 자체 포함 단일 파일이 실행할 때마다 자기를

대가는 **빌드 머신에 MSVC C++ 빌드 도구 의존**이다. 스크립트가 없으면 명확히 죽게
했고, 주석에 "프레임워크 의존으로 우회하지 말 것" 을 박아 뒀다 — 우회하면 위 실패가

### 밟은 것

**25. `vswhere` 가 PATH 에 없으면 MSVC 가 있어도 AOT 가 실패한다**
에러가 `link.exe` 를 가리켜서 **C++ 도구가 없는 것처럼 보인다.** 실제로는 AOT 링크
단계가 `vswhere.exe` 로 MSVC 를 찾다가 실패하고, 그 실패 메시지가 링커 명령줄 안으로
섞여 들어간다. 설치 경로(`C:\Program Files (x86)\Microsoft Visual Studio\Installer`)를
PATH 앞에 붙이면 바로 된다. 스크립트가 처리한다.

**26. `Start-Process -PassThru` 의 종료 코드는 `-Wait` 없이는 빈 값이다**
Windows PowerShell 5.1 에서 `-Wait` 를 준 경우에만 `.ExitCode` 가 채워진다.
`WaitForExit()` 을 직접 불러도 비어 있다(세 조건으로 확인했다). **그런데 빈 값은
비교에서 조용히 거짓이 된다** — 검증이 실제로는 PASS 인데 화면에는
`스팀 초기화 FAIL (종료 코드 )` 로 찍혔다. 숫자가 빠진 걸 눈으로 보고서야 알았다.
`-Wait` 에는 타임아웃이 없어서 빌드가 영원히 멈출 수 있으므로, .NET `Process` 를
직접 쓰는 `Invoke-Native` 로 갈았다.

**검증 코드가 조용히 무의미해지는 것이 검증이 없는 것보다 나쁘다.** 없으면 없는 줄
알지만, 있으면 통과했다고 믿는다.

**27. 새 ps1 은 UTF-8 BOM 으로 저장해야 한다**
BOM 없이 저장했더니 `powershell -File` 이 ANSI 로 읽어서 한글 주석이 깨지고,
깨진 바이트가 따옴표를 망가뜨려 **파싱 에러가 스크립트 중간 여기저기서** 났다.
원인이 인코딩인데 에러는 문법으로 보인다. 기존 `tools/*.ps1` 이 전부 BOM 이 있는
이유가 이것이었다.

### 세이브 파일에 쓰는 주체가 둘이 되는 순간 (B5)

B5 의 진짜 문제는 저장 코드가 아니라 **경합**이었다. 셸이 `settings` 를, 게임이
`tree`/`bananas`/`totalKeystrokes` 를 쓴다. 양쪽이 각자 "읽고 → 자기 몫만 고치고 →
통째로 쓰기" 를 하면 사이에 낀 상대의 변경이 사라진다. **드래그 한 번에 바나나가
되돌아가는** 종류의 버그이고, 타이밍에 달려 있어 재현이 어렵다.

`ISaveStore` 로 소유자를 하나로 묶었다. 세션에 `SaveData` 인스턴스는 하나뿐이고,
셸도 게임도 같은 객체를 고친 뒤 `MarkDirty()` 만 부른다. 디스크 쓰기 시점은 플랫폼이
혼자 정한다(최소 10초 간격). **경합이 구조적으로 생길 수 없다.**

덤으로 셸이 드래그·옵션 변경마다 하던 `SaveIO.Load()` 디스크 읽기가 없어졌다.

**`lastQuitUtc` 를 "마지막으로 저장한 시각" 으로 다시 읽었다.** 매 쓰기마다 시각을
찍으면 정상 종료와 강제 종료가 **같은 경로**가 된다 — 크래시로 마지막 10초를 잃어도
다음 실행의 오프라인 성장이 그 10초를 벽시계 기준으로 그대로 메운다. 상주 앱은
강제 종료가 잦다(§7-5)는 전제에 맞는 동작이다. 필드 이름은 스키마 계약이라 그대로 뒀다.

오프라인 성장은 **슬롯마다 따로 상한에 걸린다.** 3일을 비워도 3개다 — 경제가 시간이
아니라 슬롯 수에 묶여 있다는 §2-2 설계가 여기서 실행되고, `lastQuitUtc` 를 조작해도
무한 파밍이 안 되는 이유이기도 하다.

### 클릭 통과 창에서 UI 가 입력을 받는 법

이 게임의 오버레이는 **나무와 원숭이 영역만 클릭을 받고 나머지는 통과시킨다**
(§7-1). 상점을 열면 창 전체가 클릭을 받아야 하는데, 셸은 옵션 창을 열 때
`WindowSetMousePassthrough(빈 배열)` 로 이 문제를 푼다 - 하지만 **그건 platform/
코드이고 게임 레이어가 부를 수 없다** (§8-3 폴더 소유권).

그래서 계약만으로 풀었다. `IInteractiveArea.GetClickableBounds()` 가 상점이 열린
동안 **창 전체**를 신고한다. 셸은 매 프레임 이 값을 읽어 passthrough 를 다시
계산하므로(`OverlayShell.CurrentHitRect`), **플랫폼 코드는 한 줄도 안 바뀌었다.**

창 전체를 이 계약의 좌표계(부모 로컬)로 옮기는 데 역변환이 필요하다 - 셸 루트에
배율이 걸려 있고 플랫폼이 그 배율을 **다시** 곱하기 때문이다. 그냥 뷰포트 값을
넘기면 배율이 두 번 곱해진다.

상점 버튼도 같은 이유로 자리가 정해졌다. `Rect2.Merge` 는 외접 사각형이라 버튼을
화면 반대편에 두면 **그 사이의 빈 공간까지 전부 클릭을 먹는다.** 원숭이 바로
아래에 붙여서 영역이 거의 안 늘어나게 했다.

### 상점과 장착을 한 화면에 합쳤다

## 2026-09-21 (넷째) — B7 도감. 상점 목록과 일부러 다르게 그렸다

§3-3 이 요구한 셋을 전부 붙였다 — 도감 화면, **메인 화면 구석의 수집률**,

### 도감을 따로 만들 이유가 있는가

상점이 이미 16종을 전부 보여 주고 있어서(§3-2 "전 상품 상시 노출") 도감이
같은 정보를 반복하면 탭을 하나 더 둘 이유가 없다. 그래서 **보는 목적을 갈랐다**:

- **상점 목록** = "무엇을 살까". 세로 목록, 이름·가격·버튼
- **도감** = "얼마나 모았나". 슬롯별 그리드, 진행 바, 슬롯별 n/m

그리고 **안 가진 것은 실루엣**으로 둔다. 무엇이 남았는지는 보이되 그림은 안
보여 주는 쪽이 모으고 싶게 만든다. `Modulate` 를 곱하는 것이라 투명한 배경은
그대로 투명하게 남는다 — 알파를 건드리면 칸 모양이 무너진다.

HUD 쪽은 반대로 **작게** 넣었다. 이 창은 바탕화면 위에 상시로 떠 있어서 크게
넣으면 일하는 내내 거슬린다. 자랑 지표는 도감 탭이 맡고, 구석의 숫자는 "아직
다 안 모았다" 만 알려 주면 된다.

### 밟을 뻔한 것

**같은 화면에 15/16 이 93% 와 94% 로 동시에 보였다.** HUD 는 정수 나눗셈
(내림), 상점 머리말은 `:0` 포맷(반올림)을 썼다. 둘 다 내림으로 통일했다.

**상점 버튼이 클릭 영역 밖으로 빠질 수 있었다.** `GetClickableBounds` 가
`_shopButton.Size` 를 그대로 믿는데, 레이아웃이 돌기 전에는 (0,0) 이라 버튼
자리에 점 하나만 합쳐진다. 그러면 버튼 가운데가 영역 밖이라 **눌러도 아무 일이
안 일어난다.** `GetCombinedMinimumSize()` 와 큰 값을 쓴다.

**하루 종일 클릭 자동화에 속았다.** 버튼이 안 먹는 줄 알고 코드를 두 번 고쳤는데,
원인이 두 개 다 환경이었다 — ① 다른 상시 최상위 창(메신저)이 창 아래쪽을 덮고

## 2026-09-23 — 경제를 서버로 옮겼다. 커서 장식은 스팀 인벤토리로

### 구조

- **진실은 둘로 나뉜다.** 잔액·나무 슬롯·강화는 D1 원장에, 장식 소유는 스팀
  인벤토리에 둔다. 구매는 서버가 "잔액 차감 + 스팀 지급" 을 한 트랜잭션으로 한다
- **하베스트는 낙관적으로 처리한다.** 클라이언트가 먼저 +1 을 그리고 백그라운드에서
  확인받는다. 구매는 응답을 기다린다(비동기 `OnBuyRequested`)
- `Tree` 는 성장 타이머를 직접 계산하지 않는다. `SyncSlots` 로 받은 값을 그리기만 한다
- **소유 조회는 백엔드를 거치지 않는다.** 조회에는 신뢰 문제가 없어서 스팀
  클라이언트 SDK 로 직접 읽는다. id↔itemdefid 매핑은 `server/src/catalog.ts` 와
  손으로 맞췄다
- 릴리스는 항상 실물을, 디버그는 기본으로 목을 쓴다(`--real-economy` 로 실물 강제).

  클라이언트가 스스로 바꾸는 통로를 열지 않기 위해서다
- 세이브 v4 는 값을 옮기지 않고 필드만 지웠다. 출시 전이라 실사용 세이브가 없다

### 밟은 것

**"Cloudflare 가 스팀을 막는다" 는 몇 시간짜리 오판이었다.** 워커에서만
`/v1/session` 이 403 이 나서 IP 차단이라고 결론 냈고, GitHub Actions 러너로
접근성 실험까지 했다(`7803813`·`8b7cfc9`·`936824e`, 이미 지움). AWS Lambda
릴레이(`server/aws-relay/`)를 만들어 배포하고 검증까지 마쳤다. 그런데 진짜
원인은 **`wrangler secret put` 의 마스킹 프롬프트를 `!` 로 중계했더니 빈 문자열이
저장된 것**이었다. `✨ Success!` 가 떴고 `secret list` 에도 이름이 보였지만 값은
길이 0 이었다. 진단 엔드포인트로 `env.KEY?.length` 를 찍고 나서야 드러났다.
→ 시크릿은 `printf '%s' "<값>" | npx wrangler secret put NAME` 으로 넣는다.
릴레이는 되돌렸고 코드는 참고용으로 남겼다. 경위는 ECONOMY-SERVER §9 에 있다.

**`AddItem` 은 HTTP 200 으로 거부한다.** `itemdefid` 를 단일 값으로 보내고
`quantity` 를 같이 보냈더니 밸브가 "No items specified" 로 조용히 거부했다. 진짜
계약은 이렇다. `itemdefid[0]`, `[1]`… 식의 배열이고, `itempropsjson` 은 필수이며,
`quantity` 파라미터는 없다. 성공 판정은 HTTP 상태가 아니라 **`X-eresult` 헤더
(`1` = OK)** 로 한다.

**인벤토리 조회 `k_EResultFail` 은 체크박스 하나 때문이었다.** 파트너 사이트의
"Inventory Service 활성화" 는 아이템 JSON 게시와 별개 스위치다.

**실측에서 버그 2개가 더 나왔다.** ① `DateTimeStyles` 조합 오류로 세션 발급이
매번 죽었다. ② `GameRoot` 가 로드 시점에 `Sync()`/`Refresh()` 를 한 번도 부르지
않아 슬롯이 항상 0개였다. 목은 둘이 서로 연결돼 있어서 가려져 있었다. 실물 둘은

  같이 고친다. 이 게임은 전역 입력을 받는 상주 앱이라 "키로거 아니냐" 가 첫 의심이고, 한 문장이라도
  틀리면 §10 이 "절대 자르지 않는 것" 으로 둔 약속이 거짓말이 된다
- 과장하지 않았다 — 서버가 있는 이상 "아무것도 수집하지 않는다" 는 거짓이다. 서버는 IP 를 저장하지 않지만
  (스키마·코드 확인) 운영사 Cloudflare 가 처리할 수는 있다고 그대로 적었다
- 확인하다 드러난 것: **외부 통신은 경제 서버 하나뿐**이다(C# 에서 HTTP 를 쓰는 곳 전수 검색). 분석·광고
  추적 코드는 없다. **로그 파일에는 스팀 이름과 SteamID 가 남는다**(`[steam] 연결됨` 줄) — 로컬 전용이라
  문구에 그대로 적었다

**쓰다가 거짓 문장을 하나 찾았다 — 옵션 "타건 카운트" 끄기가 동작하지 않는다.** 체크박스는 설정값을 저장만
하고 읽어서 세기를 멈추는 코드가 없다(9/21 할 일 목록에 "무동작" 으로 남아 있던 것). 그래서 "옵션에서 끌 수
있습니다" 는 구현 후 확정 자리로 비워 뒀다. 넣는다면 **끄면 헬퍼가 RawInput 등록 자체를 푸는 쪽**이 약속으로서
가장 강하다.

자리만 잡은 것: `[문의 이메일]`, §2-5 멀티 전송 목록(A10 이 실제로 보내는 것을 코드로 확인한 뒤 확정),
서버 데이터 삭제 절차(지금은 D1 에서 손으로). 법률 검토를 받은 문구는 아니다.

### 안 깬 도전과제 알림 (`cc90749`)

"업적을 안 깼는데 알림이 뜬다." 원인은 스팀의 **진행도 알림 `IndicateAchievementProgress`** 였다. 이걸 부르면
스팀이 **해금 토스트와 같은 우하단 자리**에 "3,288 / 10,000" 을 띄운다. 세 곳에서 부르고 있었다:

| 언제 | 뜨던 것 |
|---|---|
| 켠 뒤 첫 타건 | 다음 마일스톤까지 진행도 — 구간 기록이 -1 로 시작해서 **켤 때마다** |
| 다음 마일스톤까지 5% 넘을 때마다 | 1만 타 과제면 500타마다 |
| 구매마다 | 도감 "N/16" |

셋 다 지우고 **토스트는 해금할 때만** 뜨게 했다. 커뮤니티 페이지의 진행 막대는 `STAT_KEYSTROKES` 가 그리므로
그대로다. 계약 `IAchievements.IndicateProgress` 는 남기고 "게임 레이어는 지금 부르지 않는다 — 다시 쓰려면 이
판단부터" 를 적었다. 확인(게임 씬 단독, 목): 300+400+500타, 장식 2개 구매 → 1K·첫 구매 해금 두 줄만, 진행도
호출 0회.

A8 때 "진행도 토스트를 5%마다" 로 설계하면서 **스팀이 그걸 해금과 같은 모양으로 보여 준다는 걸** 몰랐다. 유저
입장에서 진행도와 해금은 구분이 안 되는 알림이었다.

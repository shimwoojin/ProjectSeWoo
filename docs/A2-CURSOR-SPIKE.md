## 1. 두 번째 OS 창

OS 에 직접 물어본 결과(`tools/inspect-windows.ps1`):

```
0x801A4  Engine   (제목 없음)             128x128   TOPMOST|NOACTIVATE
0x501B4  Engine   ProjectSeWoo (DEBUG)    420x560   TOPMOST
```

- 장식 창이 **별도 OS 창**으로 뜬다. `project.godot` 에 `embed_subwindows=false` 필요

  이건 기능이 아니라 사고 방지다

  아니라 DWM 합성으로 per-pixel 투명을 구현한다. 셸 창도 마찬가지다.
  **exstyle 에 LAYERED 가 없다고 투명 실패로 읽으면 안 된다**

## 2. ★ 클릭 통과 — 네 번 틀렸다 ★

이 항목 하나에서 **연달아 네 번 잘못된 구현을 했고, 네 번 다 "성공"으로 오판했다.**
매번 원인이 달랐지만 **실패 방식은 같았다 — 간접 지표를 보고 판정했다.**

| 회차 | 구현 | 무엇을 보고 성공이라 했나 | 실제 |
|---|---|---|---|
| 1차 | `Window.Flags.MousePassthrough` | (아무것도 안 봄) | 플래그가 무시됨 |
| 2차 | 창 밖 축퇴 폴리곤 | `WindowFromPoint` 통과 | 창이 통째로 잘림 |
| 3차 | `WS_EX_TRANSPARENT` | exstyle + `WindowFromPoint` | 클릭을 계속 먹음 |
| 4차 | `WM_NCHITTEST` 후킹 | 실제 클릭 — **단 표적이 같은 프로세스** | 다른 앱의 클릭을 먹음 |
| 5차 | **`TRANSPARENT`+`LAYERED`** | **유저가 메모장을 직접 클릭** | **동작** |

네 번 다 화면이나 로그로는 안 드러나는 종류였다. **4차가 가장 뼈아프다** —
대조군까지 세운 제대로 된 실험이었는데 표적이 틀렸다.

### 1차 실패 — `Window.Flags.MousePassthrough` 는 아무것도 하지 않는다

```csharp
_win.SetFlag(Window.Flags.MousePassthrough, true);   // 조용히 무시된다
```

- exstyle 에 `WS_EX_TRANSPARENT` 가 붙지 않았다
- `WindowFromPoint(장식 창 중심)` 이 **장식 창 자신**을 돌려줬다

즉 **커서를 따라다니며 유저의 클릭을 전부 먹는 상태**였다. 화면상으로는 완벽하게
정상으로 보인다 — 창은 투명하고 장식은 커서를 잘 따라온다. 유저가 장식 위를
클릭해 봐야 드러난다.

### 2차 실패 — 축퇴 폴리곤은 창을 통째로 잘라낸다

셸이 쓰는 폴리곤 API 로 바꾸면서, "전체 통과"를 표현하려고 창 밖의 축퇴 삼각형을 줬다:

```csharp
private static readonly Vector2[] NoHitRegion =
{
    new(-4, -4), new(-3, -4), new(-4, -3),   // 창 밖 = 어느 점도 폴리곤 안이 아님
};
DisplayServer.WindowSetMousePassthrough(NoHitRegion, _win.GetWindowId());
```

히트테스트는 "통과"로 바뀌었다. **그래서 성공으로 기록했다. 틀렸다.**

**Godot 의 `window_set_mouse_passthrough` 는 Windows 에서 `SetWindowRgn` 으로
구현돼 있다. 창을 물리적으로 잘라낸다.** 창 밖 폴리곤을 주면 창이 통째로 잘려
나간다. 클릭이 통과한 이유는 **거기 창이 아예 없었기 때문**이고, 같은 이유로
아무것도 안 보였다.

> 처음에 이 문서에 "Windows 에서 Godot 은 `WM_NCHITTEST` 의 `HTTRANSPARENT` 로
> 구현하므로 렌더링에는 영향이 없다"고 썼다. **근거 없는 추측이었고 사실이 아니다.**
> 히트테스트 결과 하나만 보고 기전을 지어냈다.

### 3차 실패 — `WS_EX_TRANSPARENT` 는 스타일만 붙고 클릭을 못 막는다

히트테스트만 바꾸고 렌더링은 건드리지 않는 정공법이다. 갑 담당 영역(P/Invoke ·
윈도우 핸들링)에 정확히 들어간다.

```csharp
long handle = DisplayServer.WindowGetNativeHandle(
    DisplayServer.HandleType.WindowHandle, _win.GetWindowId());
var hwnd = new IntPtr(handle);

long before = GetWindowLongPtr(hwnd, GwlExStyle).ToInt64();
SetWindowLongPtr(hwnd, GwlExStyle, new IntPtr(before | WsExTransparent));

// 반드시 되읽어서 확인한다. "걸었다"와 "걸렸다"는 다르다 — 1차 실패가 그것이었다.
long after = GetWindowLongPtr(hwnd, GwlExStyle).ToInt64();
```

`ClickThroughState` 를 리포트에 박고, `WindowFromPoint` 로 "통과" 를 확인했다.
**그래도 틀렸다.** 유저가 실제로 써 보니 클릭이 안 먹었다.

`WS_EX_TRANSPARENT` 는 붙었고(0x8200018 → 0x8200038), 창이 움직이는 내내 유지되고,
`WindowFromPoint` 도 뒤 창을 돌려준다. **그런데 실제 마우스 입력은 이 창이 먹는다.**
`WindowFromPoint` 가 실제 마우스 라우팅과 다르다는 뜻이다.

> **교훈: `WindowFromPoint` 는 클릭 통과의 증거가 아니다.** 이 항목에서 세 번 속았고
> 세 번 다 "간접 지표"를 보고 판정했기 때문이다. 실제 클릭을 쏴서 표적이 받는지
> 봐야 한다.

### 최종 — 3방식을 실제 클릭으로 비교했다

통제 실험을 짰다. **표적은 우리 셸 창이다** — 셸이 이미 `clicks on body` 를 세서
리포트에 찍으므로 외부 앱 없이 A/B 가 성립한다. 마스코트 좌표에 커서를 놓고
실제로 클릭한 뒤, 셸의 클릭 카운터가 올랐는지 본다.

| 방식 | 클릭 통과 | 화면 표시 | per-pixel 투명 |
|---|---|---|---|
| 커서 레이어 OFF (대조군) | (해당 없음) | — | 정상 |
| 클릭 통과 안 검 (대조군) | **X 먹힘** | O 보임 | 정상 |
| `WS_EX_TRANSPARENT` 만 | **X 먹힘** | O 보임 | 정상 |
| **`TRANSPARENT`+`LAYERED`** | **O 통과** | O 보임 | **정상** |
| **`WM_NCHITTEST` 후킹** | **O 통과** | O 보임 | **정상** |

대조군 두 줄이 이 표의 핵심이다. "클릭 통과 안 검" 이 **X 먹힘**으로 나와야
실험이 실제로 차이를 잡아낸다는 증거가 되고, 그게 없으면 또 속는다.

**채택: `WM_NCHITTEST` 후킹.** 둘 다 동작하지만 이쪽이 **창 스타일을 전혀 건드리지
않는다.** Godot 은 투명 창에 `WS_EX_NOREDIRECTIONBITMAP` 를 쓰는데, 거기에
`WS_EX_LAYERED` 를 얹는 건 문서화되지 않은 조합이다. 이 PC 에서는 됐지만 다른
GPU/드라이버에서 보장이 없다. 상주 앱은 남의 PC 에서 도는 게 전부라 이 차이가 크다.

```csharp
// 창의 WndProc 을 가로채 WM_NCHITTEST 에 HTTRANSPARENT 를 돌려준다.
_wndProcHook = HookProc;                 // ★ 필드로 잡아둔다. GC 되면 OS 가
IntPtr ptr = Marshal.GetFunctionPointerForDelegate(_wndProcHook);  //   죽은 포인터를 부른다 = 크래시
_originalWndProc = SetWindowLongPtr(hwnd, GwlpWndProc, ptr);
```

`--cursor-clickthru=<transparent|layered|hittest>` 로 언제든 다시 비교할 수 있다.
`layered` 는 검증된 대안으로 남겨 둔다.

### ★ 위 표는 틀린 표적으로 잰 것이다 ★

**표적이 우리 셸 창, 즉 같은 프로세스였다.** 상주 앱의 클릭 통과에서 중요한 것은
정확히 그 반대 — **다른 프로세스의 창**이 입력을 받는가다. 메모장, 브라우저, 탐색기.
유저가 실제로 상대하는 건 그쪽이고, 우리 게임 창과의 상호작용이 아니다.

그리고 같은 프로세스 표적은 **원리적으로 믿을 수 없다.** Godot 은 입력을 앱 단위로
처리하기 때문에, 장식 창 HWND 에 떨어진 클릭이 엔진 내부 입력 경로를 타고 셸 씬까지
도달할 수 있다. 즉 "셸이 클릭을 받았다" 가 "클릭이 장식 창을 통과했다" 를 뜻하지 않는다.

실사용 보고: **`hittest` 로도 메모장·브라우저 등 다른 앱의 클릭이 먹통이다.**

### 최종 답 — `WS_EX_TRANSPARENT | WS_EX_LAYERED` (실사용 확인)

`4` 키로 세 방식을 재시작 없이 전환하며 메모장을 클릭해 확인했다.

| 방식 | 같은 프로세스(우리 셸) | **다른 프로세스(메모장·브라우저)** |
|---|---|---|
| `WS_EX_TRANSPARENT` 만 | X 먹힘 | **X 먹힘** |
| **`TRANSPARENT`+`LAYERED`** | O 통과 | **O 통과 ← 채택** |
| `WM_NCHITTEST` 후킹 | O 통과 | **X 먹힘** |

**`HTTRANSPARENT` 는 프로세스 경계를 넘지 못한다.** 같은 프로세스 창에는 통해서
자동 계측이 이걸 "통과" 로 읽었고, 그래서 한 번 더 오판했다.

per-pixel 투명은 `layered` 에서도 유지된다. `SetLayeredWindowAttributes(alpha 255)` 는
균일 알파를 지정하지만, Godot 이 DWM 합성으로 그리는 per-pixel 알파는 그대로 살아남는다
(실측: 장식 주변 모서리 픽셀이 균일한 검정이 아니라 뒤 배경 색이었다).

기본값을 `Layered` 로 바꿨다. 나머지 둘은 **쓰면 안 되는 것**으로 코드에 명시했다.

> **교훈 — 표적을 틀리면 대조군을 아무리 잘 세워도 소용없다.**
> 양성/음성 대조군을 다 세우고 4/4 통과를 확인했지만, 재고 있던 대상이 처음부터
> 틀렸다. "실험 설계가 탄탄한가" 이전에 **"이게 유저가 겪는 상황인가"** 를 묻는다.

교차 프로세스 자동 측정은 세 번 시도해서 세 번 다 하네스 문제로 실패했다
(표적 창이 VS 전체화면에 가림 / 다른 topmost 창에 밀림). 자동화를 더 파는 대신
**런타임 전환 핫키를 붙여서 사람이 5초 만에 비교**하게 했다 — `4` 키.

### (참고) 같은 프로세스 표적으로 잰 결과

좌클릭만 재고 "통과" 로 판정했다가 실사용에서 안 된다는 보고를 받았다.
**좌클릭이 통과해도 우클릭·휠·드래그가 막히는 실패가 가능하고, 그건 출시 불가다.**
셸이 네 경로를 따로 세도록 고치고 각각 확인했다.

| 조건 | 좌클릭 | 우클릭 | 휠 | 드래그 |
|---|---|---|---|---|
| 장식 OFF (양성 대조군) | 2 | 1 | 1 | 1 |
| **장식 ON + `hittest`** | **2** | **1** | **1** | **1** |
| 장식 ON + 통과 안 검 (음성 대조군) | **0** | **0** | **0** | **0** |

**대조군 두 줄이 이 표를 신뢰할 수 있게 만든다.** 음성 대조군이 전부 0 이라는 것은
이 실험이 "막힘" 을 실제로 검출한다는 증거다. 그게 없으면 `hittest` 의 1 들이
"통과했다" 인지 "원래 다 1 이 나오는 실험" 인지 구분이 안 된다.

드래그는 클릭 카운터가 아니라 **셸 창이 실제로 움직였는지**로 판정한다.
누르고 떼기만 한 것과 구분하기 위해서다.

## 2-1. 진단 과정에서 배운 것

"커서에 아무것도 안 보인다"를 쫓는 데 쓴 방법들이다. 같은 증상이 또 나오면 이 순서로 간다.

### 도구를 먼저 의심한다

화면 캡처(`CopyFromScreen`)는 DWM 합성 오버레이를 못 잡는 경우가 있다. **도구가
고장난 것과 창이 안 그려지는 것이 똑같이 보인다.** 그래서 확실히 렌더되는 메인 창을
**대조군으로 같이 찍었다.** 메인 창 946색 / 장식 창 영역은 배경화면 171색 + 분홍 0 →
도구는 정상이고 창이 진짜로 안 나온다는 것이 갈렸다.

### 엔진 안과 밖을 갈라서 본다

화면에 안 보이는 원인은 둘인데 밖에서는 구분이 안 된다:

| | 렌더 타깃 | 화면 |
|---|---|---|
| (a) Godot 이 애초에 안 그렸다 | 비어 있음 | 없음 |
| (b) 그렸는데 화면에 못 올렸다 | 내용 있음 | 없음 |

`Viewport.GetTexture().GetImage()` 로 창의 렌더 타깃을 직접 읽었더니
`corner=(1.00,0.00,0.80,1.00)` — 우리가 칠한 분홍이 그대로 있었다. **(b) 확정.**
그리기가 아니라 표시 문제로 좁혀졌고, 여기서 방향이 완전히 바뀌었다.

### 의심스러운 것부터 하나씩 뺀다

(b) 라면 드라이버가 유력해 보였다. 4개 렌더러 전부 돌렸는데 **전부 똑같이
"렌더 타깃에는 있고 화면에는 없다"** 였다 → 드라이버가 아니다.

그 다음 의심한 것이 "증상이 나타난 시점"이었다. 클릭 통과를 폴리곤으로 바꾼
직후였다. 그것만 빼고 돌리니 76% 로 보였다. **범인 확정.**

### 이 프로젝트에서 실제로 밟은 도구 버그들

1. **exstyle 만 보고 판정하면 안 된다.** 실제 히트테스트(`WindowFromPoint`)를 해야 한다
2. **`LAYERED` 가 없어도 투명 실패가 아니다.** Godot 은 Windows 에서 DWM 합성으로
   per-pixel 투명을 한다. 셸 창도 `LAYERED` 없이 정상이다
3. **`Godot_..._console.exe` 는 게임을 자식 프로세스로 띄우는 래퍼다.** PID 가 다르다
4. **`user32` 의 `*W` 함수에 `StringBuilder` 를 넘길 때 `CharSet.Unicode` 가 필요하다.**
   기본값(Ansi)이면 창 제목 "Godot..." 이 "G" 로 나온다
5. **PowerShell 파이프라인은 배열을 풀어버린다.** `List<int[]>` 를 `Where-Object` 에
   통과시키면 원소가 스칼라가 된다. 0개 샘플로 "렌더 안 함" 결론이 나올 뻔했다
6. **PowerShell 은 한글도 변수명 문자로 취급한다.** `"$Seconds초"` 는 `$Seconds` 가
   아니라 존재하지 않는 `$Seconds초` 다
7. **★ 측정 프로세스가 DPI 인식이 없으면 `SetCursorPos` 가 요청한 곳에 커서를 안 놓는다.**
   요청 `(1000,500)` → 실제 `(975,599)`. Windows 가 모니터별로 좌표를 스케일링한다.
   이것 때문에 클릭 실험 두 번이 통째로 무효였고, 그 사이 "장식 창이 안 따라온다"는
   잘못된 의심까지 했다. 앱 자체는 `offset 0,0` 으로 정확했다.
   측정 스크립트 첫 줄에 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 를 건다.
   **멀티모니터 PC 에서 좌표를 다루는 도구는 이게 없으면 전부 거짓말을 한다**

## 3. 이동 주기 vs CPU

```powershell
powershell -ExecutionPolicy Bypass -File tools\measure-cursor.ps1
```

### 설계 전제

**부하는 커서 좌표를 읽는 데서 나오지 않는다.** `MouseGetPosition()` 은 싸다.
비용은 **창을 실제로 옮기는 OS 호출**에서 나온다. 그래서 독립변수는 폴링 주기이되,
실제로 보는 값은 그 결과인 `moves`(초당 창 이동 횟수)다.

**합성 경로**(`--cursor-sim`)를 쓴다. 사람이 마우스를 안 흔들면 창이 안 움직이고,
창이 안 움직이면 이 기능의 부하가 0 으로 측정된다 — **손 놓고 재는 순간 측정이
무의미해진다.** 합성 경로는 커서가 한순간도 안 쉬는 **최악 조건**이라 실사용보다
비싼 값이 나오지만, 재현 가능하고 조건 간 비교가 성립한다.

### 결과 (Debug 빌드, 조건당 30초 측정)

| # | 조건 | cpu avg | cpu peak | `priv` | 창 이동 | 이동/초 |
|---|---|---|---|---|---|---|
| 1 | cursor off (기준선) | 0.04% | 0.20% | 336MB | 0 | 0 |
| 2 | direct / 매 프레임 | 0.02% | 0.20% | 338MB | 1799 | 60 |
| 3 | direct / 16ms | 0.01% | 0.20% | 338MB | 1798 | 59.9 |
| 4 | direct / 33ms | 0.02% | 0.20% | 338MB | 900 | 30 |
| 5 | direct / 50ms | 0.01% | 0.39% | 339MB | 600 | 20 |
| 6 | direct / 100ms | 0.00% | 0.00% | 340MB | 300 | 10 |
| 7 | **spring / 16ms** | **0.42%** | **0.98%** | 342MB | 1798 | 59.9 |
| 8 | lazy / 33ms (폴백안) | 0.00% | 0.00% | 338MB | 866 | 28.9 |

### 읽어낼 것

**1. 창을 옮기는 것 자체는 사실상 공짜다.** 초당 60회 이동(2~3번)이 이동 0회인
기준선(1번)과 구분되지 않는다. 오히려 낮게 나온 칸도 있는데, 이건 **이 구간의 차이가
측정 노이즈 안에 있다는 뜻**이지 이동이 CPU 를 줄인다는 뜻이 아니다.
**§1.3 이 최대 리스크로 꼽았던 "폴링 주기 vs CPU" 는 이 환경에서 문제가 아니다.**

**2. `spring` 만 뚜렷하게 비싸다.** 반복 측정으로 노이즈와 갈랐다:

| 모드 (16ms) | 1회 | 2회 | 3회 | 평균 |
|---|---|---|---|---|
| `direct` | 0.01% | 0.00% | 0.20% | 약 0.07% |
| `spring` | 0.42% | 0.34% | 0.31% | 약 0.36% |

`spring` 은 세 번 모두 0.3% 대로 **일관되게** 높다. `direct` 는 들쭉날쭉하지만 낮다.
차이는 실체다.

> **기전은 확정하지 못했다.** "회전 애니메이션이 장식 창 재그리기를 유발한다"는 가설을
> 세웠지만, 이동 주기를 낮춰 검증했더니 `spring/50ms` 0.11% / `spring/100ms` 0.32% 로
> **이동 횟수에 비례하지 않았다.** 단일 샘플이라 노이즈일 수도 있다. 가설을 지지하는
> 데이터가 없으므로 **기전 없이 관찰만 기록한다.**

**3. 그래도 전부 목표 안이다.** 최악 조건(`spring/16ms`)의 avg 0.42% / peak 0.98% 가
유휴 1% 목표 안이고, 이건 **커서가 한순간도 안 쉬는 합성 최악 조건**의 값이다.
실사용은 이보다 싸다.

**→ CPU 는 이 기능의 제약이 아니다. 주기와 모드는 부하가 아니라 체감으로 정한다.**

**4. 커서 창의 메모리 비용은 2~6MB 다.** 336MB → 338~342MB.
[DAY1-2-SPIKE.md](DAY1-2-SPIKE.md) 의 메모리 게이트가 실패한 원인은 커서 창이 아니라
.NET 런타임 + d3d12 기준선이다. **커서 축을 접어도 메모리는 안 해결된다.**

### 4-1 을 옵션으로 빼는 것이 왜 맞는가

부하가 제약이 아니라는 것이 이미 실측으로 확인됐다(§3). **세 모드 중 무엇을 골라도
CPU 목표 안이다.** 그러면 "어느 것이 좋은가" 는 기술 판단이 아니라 취향이고,
취향은 유저마다 다르다. 개발자 둘이 합의해서 하나로 고정할 이유가 없다.

기획서 §7-4 의 옵션 목록에 "커서 장식 On-Off" 가 이미 있으므로, 그걸 3단계
(꺼짐 / 붙어있음 / 따라옴) 로 넓히면 된다. 구현 비용은 이미 치렀다 —
`CursorLayer.FollowMode` 와 이동 주기가 런타임에 바뀐다.

`lazy` 모드가 §1.3 의 폴백안이었다는 점도 그대로 살아 있다. 축이 흔들리면
기본값을 `lazy` 로 내리면 되고, 코드를 고칠 필요가 없다.

### 4-2, 4-3 을 이월해도 되는 이유

둘 다 **막히면 설계가 바뀌는 종류가 아니다.**

- 멀티모니터 경계: 어긋나면 좌표 보정 문제이고, `offset 0,0` 이 이미 확인됐으므로
  같은 모니터 안에서는 정확하다. 배율이 다른 모니터 사이가 남은 미지수다
- 전체화면 게임 위: 배타적 풀스크린에 **못 뜨는 게 정상**이다. 버그가 아니라
  "게임 실행 중엔 자동 숨김" 이라는 기능 요구사항으로 기획서 §7-1 에 이미 반영돼 있다

### 4-1. 고무줄 / 매달린 느낌 (§1.3-2) — 옵션 기본값 정할 때

`1` 로 세 모드를 오가며 본다. **부하는 이미 통과했으므로 순수하게 체감으로 고른다.**

- `direct` — 지연 없음. 장식이 커서에 "박혀" 있다. 안전하지만 밋밋한가?
- `spring` — 뒤따라온다. 이 지연이 **거슬리는가, "매달린" 연출이 되는가**
- `lazy` — 근처에 상주하며 느슨하게. §1.3 의 폴백안

각 모드에서 `F12` 로 주기를 바꿔 가며, **주기가 낮아질 때 끊겨 보이기 시작하는 지점**을
찾는다. 그게 실제 출하값의 하한이다.

### 4-2. 멀티모니터 경계 (§1.3-3)

**이 PC 는 모니터 3대다**(9/13 기록의 "1대"는 오기록이었다. DAY1-2-SPIKE.md §4 참고).
팀원 환경을 기다릴 필요가 없다.

- 커서를 모니터 경계 너머로 천천히 옮긴다. 장식이 따라오는가, 경계에서 걸리는가
- **배율이 다른 모니터** 사이를 넘을 때 장식이 커서에서 어긋나는가 (DPI 좌표 문제)
- 빠르게 홱 넘길 때

### 4-3. 전체화면 게임 / 브라우저 / 작업표시줄 위 (§1.3-4)

- 보더리스 풀스크린 게임 위 → 보이는가 / 게임 FPS 가 떨어지는가
- 배타적 풀스크린 → **못 뜨는 게 정상**이다. 버그가 아니라 "게임 실행 중 자동 숨김"
  이라는 기능 요구사항으로 확정한다 (기획서 §7-1)
- 브라우저 스크롤 / 작업표시줄 / 시작 메뉴 위

### 4-4. 클릭 통과 (§1.3-5) — **완료**

`WS_EX_TRANSPARENT | WS_EX_LAYERED` 로 해결했다 (§2). 다른 프로세스(메모장·브라우저)의
클릭이 정상 통과하는 것을 실사용으로 확인했다.

A5 정식 구현에서 회귀가 의심되면 `4` 키로 세 방식을 재시작 없이 비교할 수 있다.
**검증은 반드시 다른 앱을 클릭해서 한다.** 우리 게임 창을 표적으로 쓰면 통과하는
것처럼 보이지만 실제로는 막혀 있을 수 있다 — 이 프로젝트에서 실제로 그렇게 오판했다.

## 6. 설계 시사점 (A5 정식 구현으로 가져갈 것)

1. **`ICursorLayer.IsSupported` 는 창을 띄운 뒤에 판정해야 한다.** Godot 은 Window 노드가
   보이게 될 때 비로소 OS 창을 만든다. 숨긴 상태의 `GetWindowId()` 는 `-1` 이다.
   이 프로젝트에서 처음에 이걸 "메인 창 id 가 아니니 성공"으로 읽어 오판했다
2. **클릭 통과는 `WM_NCHITTEST` 후킹으로 한다 (§2).** 나머지 셋은 전부 실패한다:
   `Window.Flags.MousePassthrough` 는 무시되고, `WindowSetMousePassthrough` 는
   `SetWindowRgn` 이라 창을 잘라내고, `WS_EX_TRANSPARENT` 만으로는 클릭을 못 막는다.
   창을 켤 때마다 다시 걸어야 하고, **후킹 델리게이트는 반드시 필드로 잡아둔다**
   (GC 되면 OS 가 죽은 함수 포인터를 불러 프로세스가 죽는다)
2-1. **검증은 반드시 실제 클릭으로 한다.** exstyle 되읽기도, `WindowFromPoint` 도
   통과라고 하면서 실제로는 클릭을 먹은 전례가 있다. 대조군을 같이 돌려서
   실험이 차이를 잡아낸다는 것까지 확인한다
3. **모드·주기는 옵션으로 노출한다 (2026-09-14 확정).** 부하가 제약이 아니므로
   기술 판단이 아니라 취향의 문제다. 기획서 §7-4 의 "커서 장식 On-Off" 를
   3단계(꺼짐 / 붙어있음 / 따라옴)로 넓힌다. 구현 비용은 이미 치렀다 —
   `FollowMode` 와 이동 주기가 런타임에 바뀐다
4. **`lazy` 폴백안은 이미 동작한다.** 커서 축이 흔들려도 즉시 내려갈 수 있는 자리가 있다

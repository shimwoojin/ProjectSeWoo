## 0. 이번 주의 목표는 "게임 정하기"가 아니다

검토 문서 결론대로, 세 기획(끼끼 아일랜드 / Punchy / Tiny Quest)은 **껍데기가 같고 콘텐츠만 다르다.**
껍데기 = ① 데스크톱 오버레이 셸 ② 글로벌 키 입력 카운트 ③ 상시 상주 저부하.

이번 주에 답해야 할 질문은 딱 하나:

> **"이 껍데기가 Godot 4.7 + Windows에서, 우리 손으로, 이번 주 안에 서는가?"**

Yes → 기획 3안 중 아무거나 골라도 된다.
No → 기획 회의는 전부 무의미했다. 엔진이나 성장 소스를 바꿔야 한다.

그래서 **기획 회의보다 스파이크(검증용 최소 코드)가 먼저다.**

## 1. Day 0 (오늘, 1~2시간) — 갈림길 정리

### 1-1. git 초기화
프로젝트가 아직 git repo가 아니다. 2인 작업이므로 오늘 처리.

```
git init
git add . && git commit -m "chore: godot 4.7 empty project"
```

`.gitignore`에 `.godot/`는 이미 있음. C#으로 가면 `.mono/`, `bin/`, `obj/` 추가 필요.

### 1-2. 언어/런타임 결정 — 이번 주 최대 분기점

현재 프로젝트는 **GDScript 전용 빌드**다. 네이티브 입력 후킹을 하려면 셋 중 하나를 골라야 한다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. Godot .NET + C# P/Invoke** | Godot .NET 빌드로 전환, C#에서 `user32.dll` 직접 호출 | 코드 한 덩어리, C++/C# 배경과 맞음, 자료 많음 | 배포 용량 증가, .NET 런타임 상주 메모리(상주 앱엔 불리), Godot 문서/샘플은 GDScript 기준 |
| **B. GDScript + GDExtension(C++)** | 후킹만 C++ 모듈로 | 런타임 가장 가벼움 | 빌드 체인(SCons) 세팅 비용 큼. 처음 쓰는 엔진에서 1주 안엔 비현실적 |
| **C. GDScript + 별도 헬퍼 exe** | 작은 C# 콘솔 앱이 후킹, 파이프/파일로 카운트만 전달 | **리스크 격리**: 백신 오탐이 나도 게임 본체는 깨끗. 유저가 헬퍼만 꺼도 게임은 동작 | 프로세스 2개 = 자동시작·스팀 배포·종료 처리 복잡 |

**권장: A로 시작. Day 2-3 스파이크에서 백신 오탐이 심하면 C로 선회.**
(C는 임시방편이 아니라 실제로 꽤 좋은 안이다. 오탐 실측 결과를 보고 판단.)

> ⚠️ Godot .NET 빌드는 **별도 다운로드**다. 지금 설치된 게 표준 빌드면 `Godot_v4.7-stable_mono_win64`를 따로 받아야 하고, 프로젝트를 열면 `.csproj`/`.sln`이 생성된다. .NET SDK도 필요.

### 1-3. 스팀 행정 트랙 착수 (개발과 무관하게 시계가 돈다)

## 2. Day 1-2 — 오버레이 셸 스파이크 (담당: A)

### 목표 산출물
투명 · 무테 · 항상 위 · 클릭 통과 창에 스프라이트 하나가 떠 있고, 몸통을 드래그하면 따라오고, 몸통 밖은 뒤에 있는 창이 클릭된다. 유휴 CPU 1% 미만.

### 세팅 (Project Settings)

```
display/window/size/transparent                 = true
display/window/per_pixel_transparency/allowed   = true
display/window/size/borderless                  = true
display/window/size/always_on_top               = true
```

\+ 루트 Viewport `transparent_bg = true`

### 핵심 API

| 목적 | API |
|---|---|
| 클릭 통과 영역 지정 | `DisplayServer.window_set_mouse_passthrough(PackedVector2Array)` |
| 창 이동(드래그) | `DisplayServer.window_set_position()` / `get_window().position` |
| 모니터 수·영역·DPI | `DisplayServer.get_screen_count()`, `screen_get_usable_rect()`, `screen_get_scale()` |
| 유휴 부하 | `OS.low_processor_usage_mode = true`, `OS.low_processor_usage_mode_sleep_usec`, `Engine.max_fps` |
| 트레이 아이콘 | `DisplayServer.create_status_indicator(icon, tooltip, callable)` — **Godot 4.3+ 내장. Windows/macOS 지원, Linux 미지원.** 플러그인 불필요 |

### 반드시 실측할 알려진 이슈

1. **흰색 깜빡임** — `window_set_mouse_passthrough` + 투명창 조합에서 런타임 플리커 리포트가 있다 ([godot#80098](https://github.com/godotengine/godot/issues/80098)).
   → 회피 가설: passthrough 폴리곤을 **매 프레임 갱신하지 말고 상태가 변할 때만** 갱신. 이 가설이 통하는지 확인.
2. **투명 + always_on_top 조합** — 창 상호작용 불가 / 브라우저 프리즈 리포트가 있다. 우리 환경에서 재현되는지.
3. **전체화면 게임 위에서의 동작** — 배타적 풀스크린 위에는 못 뜨는 게 정상. 보더리스 풀스크린은? 게임 프레임을 떨어뜨리는가?
   → 못 뜨는 게 확정되면 그건 버그가 아니라 **"게임 실행 중엔 자동 숨김"이라는 기능 요구사항**이다. 기획서에 반영.
4. **DPI 스케일링 125%/150%** 모니터에서 좌표가 어긋나는지.

### 합격 기준 (숫자로)

- [ ] 유휴 CPU **< 1%** (작업관리자 10분 관찰)
- [ ] ~~메모리 **< 150MB** (C#이면 .NET 런타임 포함해서)~~ → **2026-09-16 재설정:
      개인 작업 집합(`PrivWS`) < 300MB.** 실측 결과 이 예비 목표는 Godot+.NET
      호스팅 자체의 기본 비용(약 100MB 안팎)을 감안 안 한 숫자였다. 경위는
      docs/A7-PERF.md §4
- [ ] 노트북 1시간 상주 후 Windows 배터리 사용량에서 "보통" 이하
- [ ] 듀얼 모니터 간 드래그 이동 정상, DPI 다른 모니터에서도 정상
- [ ] 플리커 없음 (또는 회피책이 통함)

**하나라도 크게 깨지면 → 엔진 재검토 신호. Day 2 끝에 판정.**

## 3. Day 2-3 — 글로벌 입력 스파이크 (담당: A) ★프로젝트 최대 리스크★

### 왜 최대 리스크인가

`SetWindowsHookEx(WH_KEYBOARD_LL)`은 **키로거와 코드 시그니처가 같다.**

- Defender/SmartScreen 경고 거의 확정 + 코드 사이닝 없으면 "알 수 없는 게시자"
- 스팀 리뷰에 "키로거 아니냐" 글 하나면 끝
- Vanguard(발로란트)/EAC/BattlEye가 저수준 훅을 차단하거나 문제 삼음 — 게이머 대상 상주 앱인데 치명적

### 3안 비교 — 셋 다 만들어서 실측

| 방식 | 얻는 것 | AV/안티치트 리스크 |
|---|---|---|
| `WH_KEYBOARD_LL` | 정확한 타수 | **높음** — 전형적 키로거 패턴 |
| **`RawInput` (`RIDEV_INPUTSINK`)** | 정확한 타수, 포커스 없어도 수신 | **중** — 훅이 아니라 등록 방식. 오탐이 덜하다고 알려짐 |
| **`GetLastInputInfo`** | 타수 아님. **마지막 입력 이후 경과시간**만 | **없음** — 후킹이 아니라 API 호출 하나 |

> `GetLastInputInfo`는 "타수"를 못 준다. 하지만 **"지금 PC 앞에서 일하는 중인가"는 정확히 준다.**
> 검토 문서 §2-1의 "이중 성장 소스(시간=기본, 타이핑=배수)" 설계와 붙이면,
> **키 후킹이 전부 실패해도 게임은 성립한다.** 이게 프로젝트의 안전망이므로 Day 2에 이것부터 30분 안에 만들어 둔다.

### 설계 원칙 (오탐 방어이자 마케팅 자산)

- **키 코드를 절대 읽지 않는다. 카운트만 증가.** 콜백에서 `vkCode`를 변수에 담지도 않게, 코드 구조로 증명 가능하게.
- 저장/전송 없음. 로컬 정수 하나.
- 이 사실을 스토어 페이지 + 게임 내 최초 실행 화면에 명시.

### 측정 항목

- [ ] Defender 실시간 검사 **켠 채로** 빌드 실행 → 차단/격리되는가
- [ ] VirusTotal 업로드 → 탐지 엔진 개수 (3방식 각각)
- [ ] 발로란트(Vanguard) 실행 중 앱 기동 → 차단/크래시 여부
- [ ] EAC 계열 게임 동시 실행
- [ ] 입력 지연 체감 (훅이 타이핑을 느리게 만드는가) — 이거 하나로 유저 다 나간다
- [ ] 초당 입력 캡(8~12타/s) + 동일 키 연타 감쇠 어뷰징 방어가 실제로 동작

### 합격 기준

| 결과 | 결정 |
|---|---|
| RawInput: VirusTotal 오탐 ≤3, Defender 무경고, Vanguard 충돌 없음 | **RawInput 채택** |
| RawInput은 걸리는데 별도 헬퍼 exe로 빼면 본체가 깨끗 | **Day 0의 C안으로 선회** |
| 셋 다 문제 | **`GetLastInputInfo` 단독 + 시간 기반 성장으로 기획 축소.** 프로젝트는 산다 |

### 병행 조사 (30분, 코딩 아님)

코드 사이닝 인증서. 개인 개발자는 OV/EV 인증서 비용·발급 기간이 크고, 저가 옵션은 사업자 요건이 붙는 경우가 있다. **"1.0을 사이닝 없이 간다면 SmartScreen 경고를 유저에게 어떻게 안내할 것인가"** 까지가 이번 주 결론이어야 한다.

## 7. Go / No-Go 판정 매트릭스 (Day 6 아침)

| 항목 | Go | 조건부 Go | No-Go |
|---|---|---|---|

## 9. Godot 처음 쓰는 사람의 최소 학습 범위 (하루 이상 쓰지 말 것)

이번 주에 필요한 것만:

1. **Node / Scene / 씬 인스턴싱** — 이게 Godot의 전부다
2. `_ready()` / `_process(delta)` / `_input()` 생명주기
3. **Signal** (연결 = 이벤트 버스)
4. `Node2D` vs `Control` 차이 — UI는 Control, 캐릭터는 Node2D
5. `res://` (읽기전용, 빌드에 포함) vs `user://` (세이브)

7. `AnimationPlayer` / `AnimatedSprite2D`

**안 배워도 되는 것:** 3D 전부, 물리 엔진, 네비게이션, 멀티플레이 API, 셰이더(초기엔).
